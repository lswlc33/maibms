## 1.1 这是什么协议

蚂蚁 BMS 蓝牙协议是蚂蚁（ANT）智能锂电池保护板用于**手机 App ↔ BMS 主板**之间通信的私有协议。
它运行在 BLE（低功耗蓝牙）之上，采用类 Modbus 的「功能码 + 寄存器 + 数据 + CRC」帧结构，
设备侧同时扮演 GATT 服务端和协议从机两个角色。

一句话概括通信模型：

> 手机往**写特征值**写一条命令帧，BMS 处理后往**通知特征值**推回应答帧。
> 一问一答，一问也可以多答（组合帧）。

它不是标准 Modbus（没有从机地址语义、寄存器是字节偏移不是 16 位寄存器地址、CRC 覆盖范围不同），
但沿用了 Modbus 的功能码思路和 CRC16-Modbus 校验算法，熟悉 Modbus 的人上手很快。

## 1.2 整体架构

```
┌──────────────────────────────────────────────┐
│  手机 App（微信小程序 / 自研客户端）           │
│                                              │
│  ┌────────────────┐   ┌───────────────────┐  │
│  │ 业务层          │   │ 协议层             │  │
│  │ 实时数据 / 参数 │──▶│ 组帧 拆帧 CRC 解码 │  │
│  │ 控制 / 升级     │◀──│ 功能码分发         │  │
│  └────────────────┘   └───────────────────┘  │
│           │                    │             │
│           ▼                    ▼             │
│  ┌────────────────────────────────────────┐  │
│  │ 传输层：微信 BLE API / 原生 BLE 栈      │  │
│  └────────────────────────────────────────┘  │
└──────────────────────┬───────────────────────┘
                       │  BLE GATT
                       │  服务 FFE0
                       │  写 FFE1 ▶   ◀ 通知 FFE1
                       │  （备选 FFF3/FFF4、FFF5/FFF6）
┌──────────────────────▼───────────────────────┐
│  蚂蚁 BMS 主板                                │
│  ┌──────────────┐  ┌──────────┐  ┌────────┐  │
│  │ 蓝牙模组      │─▶│ 主控 MCU │─▶│ 采集芯片│  │
│  │ （地址 A1）   │  │          │  │（地址A0）│ │
│  └──────────────┘  └──────────┘  └────────┘  │
│         │                │                    │
│         │ 可选：DTU 模组（4G/GPS，地址经 53）  │
└──────────────────────────────────────────────┘
```

要点：

- **BMS 主板**是 BLE 外设，默认协议地址 `A1`；总线上若有第二台设备（如并机），地址为 `C1`。
- **采集芯片（AFE）** 有独立的地址 `A0` 和指令族（功能码 `59` / `70`），用于均衡控制、线阻测量、芯片升级。
- **DTU 模组**（4G/GPS）通过功能码 `53` 间接控制，命令由 BMS 转发。

## 1.4 五个贯穿全篇的设计特点

### ① 功能码成对出现

请求与响应靠功能码区分，规律是 **响应 = 请求 + 0x10**：

```
请求 01（读实时）  →  响应 11
请求 02（读参数）  →  响应 12
请求 51（控制）    →  响应 61
请求 53（DTU）     →  响应 63
```

写参数类是例外，用 **+0x20**：`22→42`、`23→43`、`26→46`。
这个规律让抓包时能立刻判断一条报文是「命令」还是「应答」。

### ② 一切小端

帧头里的寄存器、数据区里的所有多字节数值，**一律低字节在前**。

```
寄存器 330  →  线上 4A 01
值 3650     →  线上 42 0E
CRC 0x6258  →  线上 58 62
```

唯一的例外是**字符串**（版本号、密码、ID），按字节顺序原样排列。

### ③ CRC 用「低字节在前」，且覆盖范围看帧类型

| 帧类型 | 判定条件 | 帧长 | CRC 覆盖 |
|---|---|---|---|
| 短帧（读命令） | 功能码 < 0x10 | 固定 10 字节 | `[1 .. 5]`（地址到长度字节） |
| 长帧（应答 / 带数据） | 功能码 ≥ 0x10 | `10 + N` | `[1 .. 5+N]`（地址到数据末） |

CRC 算法是标准 CRC16-Modbus，但**校验值低字节先写**。
细节见 [第 3.4 节](03-帧格式与校验.md#34-crc-校验)。

### ④ 长度字节有两种含义

同一位置的第 6 个字节：

- 在**短帧**里是「**要读多少字节**」（请求长度）
- 在**长帧**里是「**实际带了多少字节**」（数据长度）

这是解析器区分两种帧的依据，也是最容易搞混的地方。

### ⑤ 一问一答 + 主动轮询

BMS **不会主动推送**实时数据，必须由 App 每 500 ms 轮询一次 `0x01`。
只有事件日志、升级状态等少数场景由设备侧在应答中携带。
所以任何对接程序的首要任务就是维持这个轮询心跳 —— 停轮询就收不到数据。

## 1.5 术语表

| 术语 | 含义 |
|---|---|
| **帧** | 一次完整的协议报文，`7E … AA 55` 包裹 |
| **短帧** | 无数据区的 10 字节帧，用于读命令 |
| **长帧** | 带数据区的帧，用于应答与写命令 |
| **组合帧** | 一次通知里含两段帧，第二段省略帧头、共用一个 `AA 55` |
| **功能码** | 帧里标识「要做什么」的字节，如 `0x51` |
| **寄存器** | 2 字节的地址或命令号，含义由功能码决定 |
| **地址** | 帧第 2 字节，标识总线上哪台设备：`A1` 主机 / `C1` 第二台 / `A0` 采集芯片 |
| **通道** | 一组「写特征值 + 通知特征值」的配对，如 `ffe1` |
| **AFE** | 采集芯片（Analog Front End），负责单体电压采集与均衡 |
| **DTU** | 4G/GPS 通信模组 |
| **倍率 / range** | 解码除数，如 ÷1000 表示原始值除 1000 |
| **主动均衡** | 带能量转移的均衡方案（机型 `double_balance` 等） |
| **机型 / bmsModel** | 由扩展帧寄存器区间标识的硬件方案，如 `home_store` |
| **权限等级** | 1~9 级，决定能否写参数、升级固件 |
