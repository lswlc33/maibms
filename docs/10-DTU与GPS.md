## 10.1 DTU 是什么

**DTU**（Data Transfer Unit）是集成 4G 通信与 GPS 定位的模组，通过串口与 BMS 主控相连。
BMS 把 DTU 当作一个外设，蓝牙协议里提供了三种与它交互的方式：

| 方式 | 功能码 | 用途 |
|---|---|---|
| 读定位数据 | `06` → `16` | 经纬度、速度、里程、SIM 信息 |
| 读写配置 | `07` → `17` / `26` → `46` | 服务器地址端口、账号密码、上传开关 |
| 发命令 | `53` → `63` | 重启、立即上报、OTA、查流量等 43 条命令 |

> 蓝牙链路上看到的 GPS 数据，实际上是 BMS 从 DTU 读取后转发给手机的。
> 下表偏移均已对照旧版 `app.js` 的解析顺序逐字节复核。

## 10.2 GPS 定位数据（0x06 → 0x16）

### 请求（短帧）

```
7E A1 06 00 00 6C CRC AA 55          （读 108 字节）
```

- 功能码 `06`，寄存器固定 `0`，长度 = 读取字节数（旧版用 108）

### 应答（长帧）数据区

| 偏移 | 长度 | 字段 | 解码 |
|---|---|---|---|
| 0 | 2 | 告警标志 | u16 |
| 2 | 2 | 状态标志 | u16 |
| 4 | 4 | 经度 | s32（需按设备定义缩放，通常 ×1e-6 或 ×1e-7） |
| 8 | 4 | 纬度 | s32 |
| 12 | 2 | 高度 | u16（米） |
| 14 | 2 | 保留 | |
| 16 | 2 | 速度 | u16 |
| 18 | 2 | 方向 | u16（0~359 度） |
| 20 | 4 | 里程 | u32 |
| 24 | 1 | 年 | **+2000**（如 25 → 2025） |
| 25 | 1 | 月 | 1~12 |
| 26 | 1 | 日 | 1~31 |
| 27 | 1 | 时 | 0~23 |
| 28 | 1 | 分 | 0~59 |
| 29 | 1 | 秒 | 0~59 |
| 30 | 1 | 4G 信号强度 | 原值 |
| 31 | 1 | 卫星数 | 原值 |
| 32 | 10 | 保留 | |
| 42 | 30 | SIM 卡号 | ASCII，去尾部 0 |
| 72 | 2 | 保留 | |
| 74 | 15 | IMSI | ASCII |
| 89 | 15 | IMEI | ASCII |

参考实现：

```python
def parse_gps(d: bytes):
    return {
        "alarm":      u16(d, 0),
        "status":     u16(d, 2),
        "longitude":  s32(d, 4) / 1e7,      # 原始值 ÷1e7 → 十进制度
        "latitude":   s32(d, 8) / 1e7,
        "altitude":   u16(d, 12),
        "speed":      u16(d, 16),
        "direction":  u16(d, 18),
        "mileage":    u32(d, 20),
        "datetime":   f"20{d[24]:02d}-{d[25]:02d}-{d[26]:02d} "
                      f"{d[27]:02d}:{d[28]:02d}:{d[29]:02d}",
        "csq":        d[30],
        "satellites": d[31],
        "sim":        ascii_str(d[42:72]),
        "imsi":       ascii_str(d[74:89]),
        "imei":       ascii_str(d[89:104]),
    }
```

> **经纬度缩放：÷1e7（即 ×1e-7）** —— 已从旧版地图页确证：
>
> ```javascript
> // pages/MapLocation/MapLocation.js
> latitude:  (Gprs_Latitude  / 1e7).toString(),
> longitude: (Gprs_Longitude / 1e7).toString(),
> ```
>
> 即原始 s32 值除以 1e7 得到十进制度数。该页的默认值是 `32.629034` / `110.798657`（湖北十堰一带），
> 与 ÷1e7 后的量级吻合。
>
> 注意经度负值表示西经、纬度负值表示南纬。
>
> > 新版的地图流程位于**未提供的分包** `pages_WifiPage`（`equipment/mapList` 等页面），
> > 因此新版侧的换算代码看不到；`updateGps` 事件在新版里只是把原始帧转发出去。
> > 若你的设备来自新版生态，建议仍按 ÷1e7 处理并实测一次确认。

### 新版推送形式

新版不再主动轮询 GPS，而是**接收设备推送**：以 `7ea11600` 开头的报文会作为 GPS 事件处理，
交由 `updateGps` 逻辑解析。这类推送同时用于「哨兵」功能（低功耗下的定时上报）。

## 10.3 GPRS / DTU 配置读写（0x07 / 0x26）

### 读配置（0x07 → 0x17）

```
请求：7E A1 07 <起始地址2B> <字节数> CRC AA 55
```

配置区是一块按地址分块的字符串/数值混合区，App 按**响应中的地址**分块解析：

| 地址 | 内容 | 长度 | 类型 |
|---|---|---|---|
| 0 | 家用服务器 DTU ID | 16 | ASCII |
| 16 | 客户服务器 DTU ID | 16 | ASCII |
| 32 | GPRS 波特率 | 2 | u16 |
| 34 | GPRS OTA 服务器 IP | 32 | ASCII |
| 66 | GPRS 用户名 | 8 | ASCII |
| 74 | GPRS 密码 | 8 | ASCII |
| 82 | GPRS 服务器端口 | 2 | u16 |
| 84 | 升级文件名 | 32 | ASCII |
| 116 | BMS OTA 服务器 IP | 32 | ASCII |
| 148 | BMS 用户名 | 8 | ASCII |
| 156 | BMS 密码 | 8 | ASCII |
| 164 | BMS 服务器端口 | 2 | u16 |
| 166 | BMS 升级文件名 | 32 | ASCII |
| 198 | 数据记录上传服务器 | 32 | ASCII |
| 230 | 数据记录上传用户名 | 8 | ASCII |
| 238 | 数据记录上传密码 | 8 | ASCII |
| 246 | 数据记录上传端口 | 2 | u16 |
| 248 | 数据记录上传文件类型 | 2 | u16 |
| 250 | 家用服务器 IP | 32 | ASCII |
| 282 | 家用服务器端口 | 2 | u16 |
| 284 | 客户服务器 IP | 32 | ASCII |
| 316 | 客户服务器端口 | 2 | u16 |
| 318 | GPRS 升级开关 | 2 | u16 |
| 320 | BMS 升级开关 | 2 | u16 |
| 322 | 数据记录升级开关 | 2 | u16 |
| 324 | 运行时间 | 2 | u16 |

> **注意**：读地址 116 且长度 ≥ 114 时，会**连续解析**从 116 开始的一整块
> （IP、用户名、密码、端口、文件名、数据记录服务器…）；
> 长度不足时只解析 IP。这是为了兼容不同固件版本的配置区长度。

### 写配置（0x26 → 0x46）

```
请求：7E A1 26 <地址2B> 02 <值2B 小端> CRC AA 55
应答：7E A1 46 <地址2B> <长度> ... CRC AA 55
```

适用于 2 字节配置项（端口、波特率、开关等）。
**字符串配置**（IP、账号密码）在旧版 App 里未开放蓝牙写入，需通过其他途径配置。

#### 结果码与实测位置（以「设置波特率」为例）

新版设置串口波特率的实现是：

```
命令：buildCommand("26", "serialPortBaudRate", 波特率值)
应答：等待功能码 "46"，事件通道名 notifylisten462800
      （= 功能码 0x46 + 寄存器字节 28 00，即地址 40）
取码：从应答字节数组的 **第 11 个字节**（索引 11）读结果码
```

| 结果码 | 含义（新版文案） |
|---|---|
| 0 | 成功（界面提示保存） |
| 1 | 权限不足 |
| 2 | 小于允许最小值 |
| 3 | 大于允许最大值 |
| 4 | 地址超限 |

> **两点值得注意**：
> ① 这套码与**写参数码表完全一致**（见 [附录 B.3](附录B-命令码表.md#b3-写参数结果码0xff-附加段)）——
> 说明「0 成功 / 1 权限不足 / 2 小于最小值 / 3 大于最大值 / 4 地址超限」是协议里通用的
> **写入结果码空间**，只是**出现位置随命令而变**（这里在整帧索引 11，写参数时在 `0xFF` 附加段的寄存器低字节）；
> ② 因此自研实现不要写死位置 —— 按协议模板的字段定义定位，或对该命令实测一次确认。
>
> 下表沿用旧版解析出的配置区地址；新版配置项的**读地址与写代码分属两套**
> （写入用命令名 + 短地址，读取用配置区长地址），见 [第 10.7 节](#107-新版实现要点)。

### 旧版实际使用的读取组合

| 请求 | 内容 |
|---|---|
| 读 116 起 114 字节 | BMS OTA 与上传配置 |
| 读 230 起 98 字节 | 数据记录上传配置 + 服务器 + 开关 |
| 读 0 起 116 字节 | DTU ID + GPRS 配置 |

## 10.4 DTU 命令（0x53 → 0x63）

### 请求（短帧或长帧）

```
7E A1 53 <命令号2B 小端> [长度] [数据] CRC AA 55

- 功能码 `53`
- 寄存器 = **DTU 命令号**

## 10.5 DTU 属性查询

命令号 `8`（DTU 属性上报）返回一大段设备属性，命令号 `9` 返回蓝牙属性。
属性数据的字段定义（按地址偏移）：

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 24 | CCID | SIM 卡号（ICCID） |
| 24 | 16 | IMSI | 国际移动用户识别码 |
| 40 | 16 | IMEI | 国际移动设备识别码 |
| 56 | 16 | DTU 硬件版本号 | ASCII |
| 72 | 16 | DTU 软件版本号 | ASCII |
| 88 | 16 | DTU 唯一码 | ASCII |
| 104 | 32 | 电池 ID | ASCII |
| 136 | 16 | BMS 硬件版本号 | ASCII |
| 152 | 16 | BMS 软件版本号 | ASCII |
| 168 | 16 | BMS 唯一码 | ASCII |
| 184 | 16 | 认证硬件版本号 | ASCII |
| 200 | 16 | 认证软件版本号 | ASCII |

> 这张表在做设备资产登记、真伪校验时很有用：

## 10.6 OTA 状态查询

命令号 `34`（查询 DTU OTA）与 `35`（查询 BMS OTA）返回升级进度：

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | OTA 状态 | 0 未开始 / 1 升级中 / 2 升级中断 / 3 升级完成 |
| 1 | 1 | 错误代码 | 0 无错误；其他见下表 |
| 2 | 1 | 进度 | 0 ~ 100 |

错误代码：

| 码 | 含义 |
|---|---|
| 0 | 无错误 |
| 1 | 未知错误 |
| 2 | 网络异常 |
| 3 | 固件不匹配 |
| 4 | 存储失败 |

App 的解析流程：读 3 个字节 → 校验错误码是否非 0 → 非 0 时把错误码翻译成文案。

## 10.7 新版实现要点

| 方面 | 新版做法 |
|---|---|
| GPS | 由主动轮询改为**推送接收**（`7ea11600` 开头的报文） |
| DTU 配置 | 通过 `0x53` 命令族的 64 字节参数命令读写（APN、WiFi、各类服务器地址） |
| DTU 保存 | 使用 `53/30`（`saveAppParam`），应答功能码 `63` |
| 参数保存分流 | DTU 参数与 BMS 参数分别保存（见 [第 7.6 节](07-控制命令.md#76-新版差异)） |
| 配置界面 | 有独立的地址设置弹窗（`addrSetPop`），字段含读写地址映射 |

新版对 DTU 配置做了「读写地址分离」：

```
字段   写地址(dataPos)   读地址(rdataPos)
APN    15               256
WiFi   16               320
其他   17~19            384 / 448 / 512
```

即写配置用命令号（短地址），读配置用配置区地址（长地址）。
