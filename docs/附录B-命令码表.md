| 寄存器（小端字节） | 功能 |
|---|---|

## B.3 写参数结果码（0xFF 附加段）

> 🟠 **实测部分验证**（2026-09-29 同上）：实测码 1（权限不够）与码 11（读取成功）；其余码未触发。

> 先澄清一个常见误解：**`0x42` 应答的数据区是参数数据块（与 `0x12` 同布局），
> 不是结果码**。写失败时的提示由同一帧里追加的 `0xFF` 段携带。

`0xFF` 段的格式：

```
功能码 = FF | 结果码（寄存器低字节）| 长度 | 参数地址 u16 | 限值 u16 | CRC
```

| 码 | 含义 | 附带数据 |
|---|---|---|
| 0 | 正常 | — |
| 1 | 权限不够 | — |
| 2 | 数据小于最小值 | 参数地址 + 最小值 |
| 3 | 数据大于最大值 | 参数地址 + 最大值 |
| 4 | 地址超范围 | — |
| 5 | 电池类型错误 / 密码不正确 | — |
| 6 | 固件升级成功（BMS） | — |
| 7 | 固件升级成功（GPRS） | — |
| 8 / 9 | 固件升级失败（BMS / GPRS） | — |
| 10 | 设置成功（需保存后生效） | — |
| 11 | 读取成功 | — |
| 16 | BOOT 固件升级成功 | — |
| 17 | 固件不匹配 | — |

> **另一处实证**：新版「设置波特率」（`26`）的 `0x46` 应答里，
> 结果码取自**整帧字节索引 11**，取值 0/1/2/3/4 分别对应成功 / 权限不足 /
> 小于最小值 / 大于最大值 / 地址超限 —— 与上表完全一致。
> 可见这套码是协议通用的「写入结果码空间」，只是**位置随命令而变**。
>
> 该码表与 DTU 命令应答（`0x63`，见 B.6）共用同一套取值。
> 6/7/8/9/16 是升级场景专用，写参数时不会出现。
>
> 新版不再硬编码这张表，改为**按服务端协议模板**判断
> （字段名含 `_success` 视为成功，`_error_min` / `_error_max` 给出限值）。

## B.4 权限结果（0x43 应答）

数据区前 2 字节 = 当前权限等级（u16 小端）：

| 值 | 能力 |
|---|---|
| 0 | 只读实时数据 |
| ≥ 1 | 可读参数 / 日志 / 身份 |
| ≥ 3 | 可写参数、执行控制 |
| 5 | 可切换 / 升级采集芯片 |
| 9 | 厂家级 |

失败表现为权限值不提升。

## B.7 采集芯片命令（0x59 / 0x70）

> ⚠ **字节序**：本节的命令码按源码命名书写，线上字节为**高字节在前**

| 其他 | — | 获取采集芯片软件版本号 | — |

## B.8 AFE 结果码（0x69 / 0x80 应答）

### 0x69（主指令应答）

**没有固定结果码表**。新版把应答交给服务端协议模板判读：
解析结果里出现名字含 `_success` 的字段即视为成功。

### 0x80（扩展指令应答）

**重启芯片 / 固定串数 / 单体累加总压上报**（数据区第 1 字节）：

| 码 | 含义 |
|---|---|
| 0 | 成功 |
| 1 | 权限不足 |
| 2 | 失败 |

> ⚠ 源码里这三个枚举的**命名**与 **desc 文案**是错位的：
> `FAIL` 的 desc 写的是「权限不足」，`NO_PRI` 的 desc 写的是「失败」。
> 上表按 **desc 文案**给出（即码 1 = 权限不足、码 2 = 失败）。
> 如果实测发现两者相反，以实测为准 —— 这是源码中需要留意的一处可疑点。

**校准时间**：

| 码 | 含义 |
|---|---|
| 0 | 成功 |
| 2 | 数据长度不是 4 |
| 3 | 时间戳无效或超出 RTC 范围 |
| 4 | 不支持的扩展地址 |

## B.9 固件升级功能码组合

| 升级目标 | 控制 | 数据 | **应答** | 说明 |
|---|---|---|---|---|
| BMS（Boot 串口） | `51` | `52` | `61` / `62` | 速率 30 |
| BMS（串口 V2） | `51` | `52` | `61` / `62` | 速率 100 |
| BMS（BLE） | `57` | `57` | `67` | |
| BMS（BLE V2） | `57` | `57` | `67` | |
| BMS Boot | `51` | `55` | `61` / `65` | |
| 采集芯片（AFE） | `59` | `59` | `69` | 速率 250 |
| 屏幕 | `56` | `56` | `66` | |
| 充电器 | `51` / `86` | `52` / `86` | `61` / `62`、`96` | |
| DTU | `53` | `54` | `63` / `64` | |

> **应答功能码全部符合「请求 + 0x10」规律**，但要注意**每个应答的来源不同**：

| 应答 | 依据 |
|---|---|
| `62` / `64` / `65` / `66` / `67` | +0x10 规律；其中 `67` 有实证 —— 源码里的保存流程监听通道名为 `notifylisten67…` |
| `96`（对 `86`） | 新版源码的响应→请求映射表 `{42:"22", 46:"26", 43:"23", 96:"86"}` |
| `61` / `63` | 源码中显式作为 ACK 参数传给等待函数 |
| `69`（对 `59`） | 源码 `setParamsApi(cmd, "69", "切换芯片")`，与 [B.7](#b7-采集芯片命令0x59--0x70) 一致 |

> ⚠ **BLE 升级（`57`）的应答功能码其实是「协议模板决定」的**：
> 源码里写的是 `this.messageArrivedAck = cmdDefine.ack` —— 期望的应答功能码来自
> 服务端下发的命令定义，而非硬编码。实际通道名为 `notifylisten67…`，
> 即**实测为 `0x67`**。自研客户端若按 0x67 实现，遇到模板变更的设备可能需要调整。

### BLE 升级阶段寄存器（代码型）

| 代码 | 线上字节 | 含义 |
|---|---|---|
| `02FF` | `02 FF` | 查询 / 启动 |
| `0CF1` | `0C F1` | 执行 BLE 升级 |
| `0DF1` | `0D F1` | 查询升级状态 |

状态码：`00` 失败 / `01` 升级中 / `02` 固件和校验不通过 / `03` 蓝牙 flash 操作失败 / `04` BMS 固件不匹配。

### 其他代码型寄存器（保存类，实测通道名）

| 功能码 | 线上字节 | 事件通道 | 用途推断 |
|---|---|---|---|
| `66` | `00 F0` | `notifylisten6600f0` | 屏幕侧保存 |
| `66` | `16 E0` | `notifylisten6616e0` | 屏幕侧保存（另一组参数） |
| `67` | `57 F0` | `notifylisten6757f0` | 蓝牙侧保存 |
| `67` | `55 F0` | `notifylisten6755f0` | 蓝牙侧保存（另一组） |
| `67` | `49 F0` | `notifylisten6749f0` | 蓝牙侧保存（另一组） |

> 这些寄存器同样**高字节在前**。用途由协议模板定义，上表为按事件通道与调用位置推断的结果。

### 升级请求包（24 字节数据）

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 16 | 标识段 |
| 16 | 4 | 固件文件长度（u32 小端） |
| 20 | 4 | 校验和（固件字节累加，u32 小端） |

### 数据包

| 项 | 值 |
|---|---|
| 每包字节数 | 128 |
| 寄存器 | 包序号（从 1 递增，小端） |
| 结束标志 | 长度为 0 |
| 完成通知 | 设备回功能码 `0xFF` |

| `0xFF`（功能码） | 升级完成通知 |

## B.11 调试参数（0x0D / 0x1D）

| 项 | 内容 |
|---|---|
| 请求功能码 | `0D`（命令名 `debugParamRead`） |
