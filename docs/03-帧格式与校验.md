## 3.1 帧结构

> ✅ **实测已验证**（2026-09-29 · 真板 `ANT@BLE24CBUB-3547`，固件 `24CBUB02-240623C`）：收发数百帧全部按此结构解析成功。

所有报文都是同一个骨架：

```
┌────┬──────┬────────┬──────────┬──────┬──────────┬────────┬───────┐
│ 7E │ 地址 │ 功能码 │ 寄存器2B │ 长度 │ 数据 N B │ CRC 2B │ AA 55 │
└────┴──────┴────────┴──────────┴──────┴──────────┴────────┴───────┘
  0     1      2       3    4       5       6..     6+N..    8+N..
```

| 字段 | 字节数 | 说明 |
|---|---|---|
| **帧头** | 1 | 固定 `0x7E` |
| **地址** | 1 | `A1` = BMS 主机（默认）；`A0` = 采集芯片（AFE）指令；`C1` = 源码将 `7EC1` 帧也当实时数据，含义未说明 |
| **功能码** | 1 | 决定本条报文做什么，见 [第 4 章](04-功能码总表.md) |
| **寄存器** | 2 | 含义随功能码变化（地址 / 命令号 / 包序号）。**字节序见下方说明** |
| **长度** | 1 | 含义见 [3.2 节](#32-短帧与长帧)，最大 192 |
| **数据** | N | 长度为零时不存在 |
| **CRC** | 2 | CRC16-Modbus，**低字节在前** |

> 地址与服务/特征无关 —— 它标识的是**同一条本地总线上的目标设备**。
> 该地址可在设备参数中修改（见下方「通讯地址与地址探测」）。
| **帧尾** | 2 | 固定 `AA 55` |

### 寄存器字段的字节序

大多数情况下是**小端**（低字节在前），但并非全部 —— 这一条直接影响能否复用样例报文：

| 功能码 | 字节序 | 例子 |
|---|---|---|
| `01` `02` `03` `04` `06` `07` | 小端 | 地址 620 → `6C 02`；地址 4096 → `00 10` |
| `22` `23` `26` | 小端 | 地址 330 → `4A 01` |
| `51` | 小端 | 命令 40 → `28 00` |
| `52`（升级包序号） | 小端 | 第 1 包 → `01 00` |
| `53`（DTU 命令） | 小端 | 命令 1 → `01 00` |
| `70` / `80`（AFE 扩展） | **高字节在前** | 命令 0x0100 → `01 00`；0x0300 → `03 00` |
| `59`（AFE 主指令） | **高字节在前** | 命令 0x00F0 → `00 F0` |
| `57`（BLE 升级阶段） | **高字节在前** | 代码 `0CF1` → `0C F1` |
| `FE`（机型区间） | 小端 | 512 → `00 02` |

> **本表是权威版本**（全量）；[第 4.4 节](04-功能码总表.md#44-寄存器字段的含义随功能码变化)与
> [附录 D](附录D-样例报文.md#关于寄存器字段的字节序重要)各有一份等价表，三处内容一致，任选一处查阅即可。

> AFE 命令的字节序依据：App 源码用 `new Uint8Array([1, 0])` 表示命令 `0x0100`、
> `[6, 0]` 表示 `0x0600`，其测试向量的寄存器参数写作 `"06 00"`；
> 采集芯片切换的常量帧为 `7E A0 59 00 F0 01 10 04 D9 AA 55`。
> 也就是说：**按源码中的命令名书写时，高字节在前**。
> 而 CRC 无论哪种情况都**始终**低字节在前。

### 通讯地址与地址探测

**通信地址本身就是两个参数**（见 [附录 A](附录A-参数寄存器表.md#a8-自定义--厂家--协议配置470--500592--786)）：

| 参数地址 | 名称 | 默认值 |
|---|---|---|
| 704 | MODBUS 通信地址 | — |
| 706 | **ANT 通信地址** | `0xA1`（十进制 161） |

另有「恢复通讯地址」命令用于把地址改回默认。

新版支持把地址字节替换为用户设定的值：

```
前缀 7EA1  →  自定义为 0x5A  →  7E5A
```

规则（源码 `applyCustomCommunicationAddress`）：4 位十六进制前缀只替换后两位，其他长度整体替换。
解析端按实际地址匹配即可。

新版在**切换 BLE 通道之前**会先做一次「通讯地址探测」，用来发现地址被改动的情况：

```
① 临时把自定义通讯地址设为 A0，发一条读命令（02 / antcomAddressRead）
② 读设备回帧里的地址字节
③ 期望得到 A1（0xA1）→ 判定"地址正常"，继续通道轮切
④ 否则判定"地址异常" → 中止操作，提示"检测到设备通讯地址被修改，请恢复通讯地址"
⑤ 无论结果如何，最后都恢复为 A1
```

> **源码中的一处疑似 bug**：判定语句写作 `"161" !== y`，
> 而 `y` 由 `toString(16).toUpperCase().padStart(2,"0")` 算得，是**十六进制字符串**（如 `"A1"`），
> 两者永不相等。
>
> 第四轮复核查清了 161 的来历 —— 它正是**参数 706「ANT 通信地址」默认值 `0xA1` 的十进制写法**。
> 可见作者本意是「设备返回的地址应等于 ANT 通信地址的默认值」，只是一边用十进制、一边算了十六进制。
> 自己实现时**直接比对 `0xA1`** 即可。

## 3.2 短帧与长帧

> ✅ **实测已验证**（2026-09-29 · 真板 `ANT@BLE24CBUB-3547`，固件 `24CBUB02-240623C`）：实测短帧长度字段 = 请求字节数（读参数 `… 02 68 00 20 …` 回 `12` 应答），长帧长度 = 数据区实际长度。

**同一个「长度」字节，在两类帧里含义完全不同**，这是解析时最关键的区分点。

| | 短帧 | 长帧 |
|---|---|---|
| 判定条件 | 功能码 **< 0x10** | 功能码 **≥ 0x10** |
| 帧总长 | 固定 **10** 字节 | `10 + N` 字节 |
| 长度字节含义 | **请求读取的字节数** | **实际携带的数据字节数** |
| 数据区 | 无 | 有，N 字节 |
| CRC 覆盖 | `[1 .. 5]`（5 字节） | `[1 .. 5+N]`（5+N 字节） |
| 典型功能码 | `01` `02` `03` `04` `05` `06` `07` | `11` `12` `13` `61` `63` … |

也就是说，**所有读命令都是短帧，所有应答和带数据的写命令都是长帧**。

```
读参数 32 字节（短帧，10 字节）：
7E A1 02 68 00 20 18 65 AA 55
      └─┬─┘     │  └─┬─┘
        │       │    └── CRC
        │       └────── 长度 = 0x20 = 32（"请给我 32 字节"）
        └────────────── 寄存器 = 0x0068 = 104（起始地址）

对应的应答（长帧，10+32 = 42 字节）：
7E A1 12 68 00 20 <32 字节数据> CRC_L CRC_H AA 55
                    └────── 长度 = 32（"这是 32 字节数据"）
```

> **长度上限**：数据区最多 **192** 字节 —— 两版解析器都写作「长度 ≤ 192 才继续处理」，
> 超过则逐字节滑动重找帧头（等同丢弃该帧）。
>
> **关于实时数据请求 245 字节的问题**：请求里的长度字段写 `245`（`0xF5`），看似超过上限，
> 但两者并不冲突 —— 请求里的 245 只是「**上限提示**」，设备返回多少由自己决定；
> 而解析端硬性要求数据区 ≤ 192。由此可推出一个实际约束：
>
> ```
> 0x11 帧完整长度 = 130 + 2N + 2M   （含扩展段）
>              ≤ 192  →  N + M ≤ 31
> 若不含扩展段：106 + 2N + 2M ≤ 192  →  N + M ≤ 43
> ```
>
> 也就是说：**「串数 + 温度数」超过 31 的设备，实时帧无法同时带扩展段** ——
> 设备要么不发扩展段，要么该帧会被 App 丢弃。
> 这是静态分析得出的推断，遇到 32S 以上的高串数设备建议实测确认。
> 新版读实时数据请求 245 字节是**请求长度**，实际应答的数据区长度由 BMS 决定
> （典型 16 串 4 温度的设备约 170 字节）。

## 3.3 组合帧

> ✅ **实测已验证**（2026-09-29 · 真板 `ANT@BLE24CBUB-3547`，固件 `24CBUB02-240623C`）：实测 `0x22 → 0x42 + FF 段`、`0x23 → 0x43 + FF 段` 两组组合帧：段 1 无 `AA55`、`AA55` 只在整条末尾。

BMS 可以在一次通知里把**两段帧拼在一起**返回，第二段**省略帧头**，两段共用一个 `AA 55`：

```
┌────┬──────┬─────────┬──────────┬──────┬─────────┬───────┐
│ 7E │ 地址 │ 功能码1 │ 寄存器1  │ 长度1│ 数据1   │ CRC1  │
├────┴──────┴─────────┴──────────┴──────┴─────────┴───────┤
│ 功能码2 │ 寄存器2 │ 长度2 │ 数据2 │ CRC2 │ AA 55         │
└──────────────────────────────────────────────────────────┘
```

第一段是标准帧头 + 标准字段；第二段从「功能码2」直接开始，没有 `7E 地址`。

### 拆分规则

设第一段数据长度为 N、第二段为 B：

| 段 | 字节范围（整条报文内） | 长度 | CRC 覆盖 | CRC 位置 |
|---|---|---|---|---|
| 第 1 段 | `[0 .. 7+N]` | `8+N` | `[1 .. 5+N]` | `[6+N, 7+N]` |
| 第 2 段 | `[8+N .. 15+N+B]` | `8+B` | `[8+N .. 11+N+B]` | `[12+N+B, 13+N+B]` |

> 第 1 段从帧头到自己的 CRC 结束共 `8+N` 字节（6 字节头 + N 字节数据 + 2 字节 CRC），
> 所以第 2 段从偏移 `8+N` 开始；整条报文最后 2 字节才是 `AA 55`。

两段 CRC **各自独立计算**，帧尾 `AA 55` 只在最末出现一次。
所以解析器需要**先校验第一段 CRC，再校验第二段 CRC**，两者都通过才接受整条报文。

### 实际用途

最常见的组合是「**实时数据 + 扩展信息**」：

```
功能码1 = 0x11（实时数据） + 功能码2 = 0xFE（扩展信息 / 机型）
```

`0xFE` 段的寄存器决定机型，详见 [第 11 章](11-采集芯片与扩展帧.md)。

> **实现提醒**：如果只解析第一段就丢弃剩余数据，会丢掉机型与主动均衡信息；
> 如果按「找到 AA 55 就算一帧结束」的简单逻辑处理，会把组合帧截断。

## 3.4 CRC 校验

> ✅ **实测已验证**（2026-09-29 · 真板 `ANT@BLE24CBUB-3547`，固件 `24CBUB02-240623C`）：真机所有收发帧（含组合帧两段）均按本文规则通过 CRC 复算。

### 算法

**标准 CRC16-Modbus**：

```
初值  0xFFFF
多项式 0xA001（反向表示的 0x8005）
对每个字节：crc ^= byte; 然后右移 8 次，每次若最低位为 1 则异或 0xA001
```

参考实现：

```python
def crc16_modbus(data: bytes) -> int:
    crc = 0xFFFF
    for b in data:
        crc ^= b
        for _ in range(8):
            crc = (crc >> 1) ^ 0xA001 if crc & 1 else crc >> 1
    return crc
```

### 覆盖范围

| 帧类型 | 覆盖字节 |
|---|---|
| 短帧 | `[1 .. 5]`：地址、功能码、寄存器低、寄存器高、长度 |
| 长帧 | `[1 .. 5+N]`：地址 到 数据末字节 |

**不包含**帧头 `7E`，**不包含**帧尾 `AA 55`。

### 线上字节顺序：低字节在前

这是最容易出错的地方。以探测帧为例：

```
计算 CRC16-Modbus("A1 01 00 00 F5") = 0x6258
线上写入顺序：先 0x58，再 0x62
```

所以校验时应当：

```
wire     = data[crc_off], data[crc_off + 1]
received = wire[1] << 8 | wire[0]        # 反过来拼
assert received == crc16_modbus(payload)
```

### ⚠ 旧版源码里的陷阱

旧版 `utils/helper.js` 的 `CheckCrc16()` **返回的是字节交换过的值**：

```javascript
CheckCrc16("A1 01 00 00 F5")  →  0x5862     // 注意：不是标准的 0x6258
```

而它的组帧代码又按「高字节先写」写出：

```javascript
o[a++] = i >> 8;      // 写 0x58
o[a++] = 255 & i;     // 写 0x62
```

两者抵消，**最终线上字节仍是 `58 62`，与标准实现完全一致**。
所以如果你照抄旧版代码，必须同时抄这两处，否则会算错。
**推荐直接使用标准 CRC16-Modbus + 低字节在前**，它与新版的 `CalculateCRC16Modbus` 一致。

## 3.5 数值编码规则

> 🟠 **实测部分验证**（2026-09-29 同上）：已实测：多字节小端、u16 组 u32（容量）、s16 负值（−2 ℃ = `FE FF`）；特殊编码（点分十进制等）未验证。

### 读取（解码）

| 类型 | 字节 | 解码 |
|---|---|---|
| `uint8` | 1 | 原值 |
| `byte` | 1 | 有符号：≥128 时减 256 |
| `uint16` | 2 | 小端无符号 |
| `short` | 2 | 小端有符号：≥32768 时减 65536 |
| `uint32` | 4 | 小端无符号 |
| `int` | 4 | 小端有符号 |
| `uint64` | 8 | 小端无符号 |
| `long` | 8 | 小端有符号 |
| `char` | N | ASCII / UTF-8，遇 `0x00` 截断 |
| `gbk-char` | N | GBK 编码（设备侧中文） |
| `split` | N | 每字节转十进制后用 `.` 连接 |
| `date` | 8 | 年(减2000)/月/日/时/分/秒 + `0000` |

**缩放**：`工程量 = 原始值 ÷ 倍率`，倍率取值与显示小数位：

| 倍率 | 小数位 | 典型用途 |
|---|---|---|
| 1 | 0 | SOC、串数、状态码 |
| 10 | 1 | 电流、总压、D/C 电压 |
| 100 | 2 | 总电压（新版） |
| 1000 | 3 | 单体电压、温度类阈值 |
| 1e6 | 1 | 容量（Ah） |
| 1e7 | 7 | 高精度量 |

### 写入（编码）

```
步骤：工程量 × 倍率 → 向下取整 → 转十六进制（定长） → 按字节倒序（小端）→ 写入数据区
```

示例：写入单体过压保护 = 3.650 V

```
3.650 × 1000 = 3650 = 0x0E42
字节倒序 → 42 0E
帧：7E A1 22 04 00 02 42 0E 4C 2C AA 55
                 └─┬─┘ └─┬─┘
              寄存器 4  数据 42 0E
```

## 3.6 组帧与解帧伪代码

### 组帧

```python
def build_frame(addr, func, reg, data: bytes) -> bytes:
    """构造一条报文。data 为空则生成 10 字节短帧。"""
    body = bytes([addr, func, reg & 0xFF, (reg >> 8) & 0xFF, len(data)]) + data
    crc = crc16_modbus(body)
    return b'\x7E' + body + bytes([crc & 0xFF, (crc >> 8) & 0xFF]) + b'\xAA\x55'


# 读实时数据（短帧：长度=读取字节数，无数据区）
build_frame(0xA1, 0x01, 0x0000, b'')                 # π 需补长度字段，见下

def build_read(addr, func, reg, count) -> bytes:
    """读命令：长度字段是请求字节数"""
    body = bytes([addr, func, reg & 0xFF, (reg >> 8) & 0xFF, count])
    crc = crc16_modbus(body)
    return b'\x7E' + body + bytes([crc & 0xFF, (crc >> 8) & 0xFF]) + b'\xAA\x55'


build_read(0xA1, 0x01, 0x0000, 0xF5)                 # → 7EA1010000F55862AA55
```

### 解帧（流式，处理粘包断包）

```python
def feed(buf: bytearray):
    """把新收到的字节追加进 buf，然后反复抽取完整报文"""
    frames = []
    while True:
        # 1. 找帧头
        i = buf.find(b'\x7E')
        if i < 0:
            buf.clear(); break
        if i > 0:
            del buf[:i]                      # 丢弃帧头之前的垃圾数据

        if len(buf) < 6:
            break                            # 头部字段还没收全

        func = buf[2]
        n    = buf[5]

        if func < 0x10:
            total, crc_off, crc_len = 10, 6, 5          # 短帧
        else:
            total, crc_off, crc_len = 10 + n, 6 + n, 5 + n

        if len(buf) < total:
            break                            # 数据还没收全

        # 2. 校验（帧尾 + CRC）
        frame = bytes(buf[:total])
        if not validate(frame):
            del buf[:1]                      # 校验失败 → 滑动一个字节重找
            continue

        frames.append(parse(frame))
        del buf[:total]

        # 3. 组合帧：若 buf 紧跟着还有一段（功能码≥0x10 起步），
        #    按"第二段"规则继续抽取，直到 buf 中不再有完整段
    return frames


def validate(frame: bytes) -> bool:
    if frame[0] != 0x7E or frame[-2:] != b'\xAA\x55':
        return False
    func = frame[2]
    n = frame[5]
    if func < 0x10:
        payload, crc_off = frame[1:6], 6
    else:
        payload, crc_off = frame[1:6+n], 6+n
    crc = crc16_modbus(payload)
    recv = frame[crc_off + 1] << 8 | frame[crc_off]
    return recv == crc
```

> 校验失败时的处理方式与 App 一致：**丢弃一个字节后重新查找帧头**。
> 这样可以自动跳过噪声、残缺报文与错位数据。
