## 12.1 升级对象与功能码

BMS 生态里有多种可升级目标，每种用不同的功能码组合：

| 升级目标 | 控制功能码 | 数据功能码 | 应答 | 速率参考 |
|---|---|---|---|---|
| BMS（Boot 串口） | `51` | `52` | `61` / `62` | 30 |
| BMS（串口 V2） | `51` | `52` | `61` / `62` | 100 |
| BMS（BLE） | `57` | `57` | `67` | — |
| BMS（BLE V2） | `57` | `57` | `67` | — |
| BMS Boot | `51` | `55` | `61` / `65` | — |
| 采集芯片（AFE） | `59` | `59` | `69` | 250 |
| 屏幕 | `56` | `56` | `66` | — |
| 充电器 | `51` / `86` | `52` / `86` | `61`/`62`、`96` | 100 |
| DTU | `53` | `54` | `63` / `64` | — |

对应关系速记（**全部符合「请求 + 0x10」**）：

```
51 → 61    BMS 串口升级控制 / 控制命令结果
52 → 62    升级数据包（BMS / 充电器）
53 → 63    DTU 升级控制 / DTU 命令结果
54 → 64    升级数据包（DTU）
55 → 65    升级数据包（Boot）
56 → 66    屏幕升级 / 保存（应答 66 也用于"操作成功"）
57 → 67    BLE 升级控制与数据
59 → 69    采集芯片升级
86 → 96    充电器 V2 / BLE 充电器升级
```

> `86` 是「请求侧同号」的一例：控制和数据都用 `86`，
> 但其**应答是 `96`**（仍满足 +0x10）。

> 「速率」是两次数据包之间的间隔参考值（`transmissionRate`），
> 值越大发送越慢 —— BLE 链路需要更慢的节奏来避免丢包。

## 12.2 升级流程总览

通用四阶段：

```
① 准备
   读取当前版本（参数区 528 / 620）
   下载固件文件（走网络，非蓝牙）
   校验固件与设备匹配

② 进入升级模式
   发送升级请求（含固件长度、校验和）
   设备回结果码，进入 Boot / 升级态

③ 传输数据
   分包写入，每包带包序号
   每包等应答（或按速率间隔连发）
   统计进度

④ 结束与校验
   发送结束包（长度 0）
   设备校验并回结果
   重启，回读版本确认
```

## 12.3 旧版流程（串口/Boot 升级）

旧版的固件升级实现较完整，可直接作为参考。

### 阶段一：准备

```
1. 读版本：7E A1 02 6C 02 20 58 C4 AA 55   （地址 620，32 字节）
   → 解析出硬件版本与软件版本 ASCII
2. 读 Boot 版本：7E A1 02 10 02 10 XX XX AA 55  （地址 528，16 字节）
3. 从服务器下载与版本匹配的固件文件
4. 载入内存：u8BinFileBuffer（最大 200 KB）
```

### 阶段二：升级请求（功能码 51，24 字节数据）

请求数据区共 24 字节：

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 16 | 保留/标识段（取固件缓冲区偏移 2048 起 16 字节） |
| 16 | 4 | **固件文件长度**（u32 小端） |
| 20 | 4 | **校验和**（固件全部字节累加，u32 小端） |

按升级目标选择命令号：

| 目标 | 命令号 | 报文 |
|---|---|---|
| BMS 升级 | 10（0x0A） | `7E A1 51 0A 00 18 <24字节> CRC AA 55` |
| DTU/其他 | 10 | `7E A1 53 0A 00 18 <24字节> CRC AA 55` |
| Boot 升级 | 43（0x2B） | `7E A1 51 2B 00 18 <24字节> CRC AA 55` |

> 校验和的作用：设备侧收到后自行校验，不匹配会拒绝升级（防固件损坏）。

### 阶段三：分包传输（功能码 52）

设备每次收到请求包后回一个**含包序号的应答**，App 据此发下一包：

```
请求：7E A1 52 <包序号2B> 80 <128字节固件数据> CRC AA 55
应答：7E A1 62 <包序号2B> <长度> <...> CRC AA 55
```

细节：

- 每包 **128 字节**（长度字段 `0x80`）
- 包序号从 1 开始递增，**小端 2 字节**
- 数据来自 `缓冲区[(序号-1) × 128]` 起的 128 字节
- 最后一包：剩余不足 128 字节时按实际长度发；**长度为 0 表示发送结束**
- 请求超时重试：App 有重试计数（旧版上限 120 次）

数据包构造伪代码：

```python
def send_firmware(fw: bytes, send_func=0x52, dev=0xA1):
    total = len(fw)
    seq = 1
    while True:
        off = (seq - 1) * 128
        chunk = fw[off: off + 128]
        if off >= total:
            chunk = b''                    # 结束包：长度 0
        frame = build_frame(dev, send_func, seq, chunk)
        ack = send_and_wait(frame)         # 等待 0x62 应答，校验序号
        if not ack:
            retry += 1
            if retry > 120: raise TimeoutError
            continue
        if not chunk:
            break
        seq += 1
```

### 阶段四：完成

- 设备回功能码 **`0xFF`** 的帧 → 表示升级成功（旧版直接弹「固件升级成功！」）
- 若走了 Boot 升级路径（命令号 43），设备先回 `0x65` 表示 Boot 就绪，再进入数据阶段
- 升级结束等待设备重启，回读版本确认新版本号

## 12.4 新版流程（BLE 升级）

新版针对 BLE 链路做了专门设计，核心是 **`0x57` 功能码**与几个固定的「阶段寄存器」：

| 代码 | 线上字节 | 名称 | 含义 |
|---|---|---|---|
| `02FF` | `02 FF` | 查询 / 启动 | 查询升级准备状态、启动升级流程 |
| `0CF1` | `0C F1` | 执行 BLE 升级 | 通知设备把已缓存的固件写入 BMS |
| `0DF1` | `0D F1` | 查询升级状态 | 返回 1 字节状态码，见下表 |

> **字节序**：这些「代码型」寄存器在源码里就是 4 个十六进制字符的字符串
> （`simpleBuildCommand(prefix, suffix, func, "0cf1", data)`），
> 由组帧函数**原样写入**，所以线上字节顺序与书写顺序一致：
> `0CF1` → `0C F1`（高字节在前）。这与读命令地址的小端写法相反，
> 详见 [第 3.1 节](03-帧格式与校验.md#寄存器字段的字节序)。
>
> **应答功能码**：由**服务端协议模板**的 `ack` 字段给出（源码 `messageArrivedAck = cmdDefine.ack`），
> 不是硬编码。实测通道名为 `notifylisten67…`，即**应答功能码为 `0x67`**（符合 +0x10 规律），
> 且应答会回显同一个代码型寄存器。

### 升级状态码（`0DF1` 查询的返回）

| 数据首字节 | 含义 | 新版提示文案 |
|---|---|---|
| `00` | 失败 | 蓝牙缓存 BMS 固件无效，执行失败 |
| `01` | 升级中 | BMS 升级中 |
| `02` | 固件和校验不通过 | 固件和校验不通过 |
| `03` | 蓝牙 flash 操作失败 | 蓝牙 flash 操作失败 |
| `04` | BMS 固件不匹配 | BMS 固件不匹配 |

> 除 `01`（继续等待）外，其余取值都应视为**终止升级并报错**。

### 流程

```
① BLE OTA 设置与使能
   53/39 (bleOta) 或 53/45 (getBleOtaSetting) —— 使能蓝牙 OTA 通道
② 发送固件到蓝牙模组（缓存）
   用 57 功能码分包写入（对齐升级类型 BMS_UP_FOR_BLE_V2）
③ 触发 BMS 升级
   发 7E A1 57 0C F1 00 XX XX AA 55    （代码 0CF1 → 线上 0C F1）
④ 轮询升级状态
   发 7E A1 57 0D F1 00 XX XX AA 55    （代码 0DF1 → 线上 0D F1）
   · 应答数据首字节 = 01 → 升级中，继续等
   · 00 / 02 / 03 / 04 → 失败，按上表给出具体原因
⑤ 成功 / 超时处理
```

### 新版的状态文案

新版按 `0DF1` 返回的状态码给出提示（见上表），常见的三条：

| 状态码 | 提示 |
|---|---|
| `00` | 蓝牙缓存 bms 固件无效，执行失败 |
| `01` | BMS 升级中 |
| `04` | BMS 固件不匹配 |

### 静默升级

新版还有「静默升级」机制（`silentUpgradeCoordinator`）：

- 在后台悄悄完成升级，不打断用户操作
- 升级期间会**暂停实时轮询**、加通道锁，避免干扰
- 需要重新握手时自动完成（`restoreSilentHomeRealtime` 之类的事件）

## 12.5 进度与状态

### 进度计算

```
进度 = 已发送字节数 ÷ 固件总字节数 × 100%
```

旧版实现：

```javascript
percentage = (u16DataAdd / nBytesToRead) * 12800
// u16DataAdd 是当前包序号，nBytesToRead 是总字节数 → 得到百分比
```

新版：

```javascript
calculateHexFileProgress(hexData, currentSeq, 128)   // → 0~1
progressCallBack(round(k * 100))
```

### 状态查询（DTU OTA）

若升级走 DTU，可用 `53/34`（查询 DTU OTA）、`53/35`（查询 BMS OTA）读进度：

| 偏移 | 字段 | 值 |
|---|---|---|
| 0 | OTA 状态 | 0 未开始 / 1 升级中 / 2 升级中断 / 3 升级完成 |
| 1 | 错误代码 | 见 [第 12.6 节](#126-失败码与排查) |
| 2 | 进度 | 0 ~ 100 |

## 12.6 失败码与排查

### 升级结果的通用结果码（`0x61` / `0x63` 应答）

| 码 | 含义 | 处理 |
|---|---|---|
| 1 | 成功 | — |
| 5 | 权限不足 / OTA 冲突 | 校验密码；或稍后重试（另一路升级进行中） |
| 6 | BMS 固件升级成功 | 成功 |
| 7 | GPRS 固件升级成功 | 成功 |
| 8 | BMS 固件升级失败 | 检查固件匹配性与供电 |
| 9 | GPRS 固件升级失败 | 同上 |
| 16 | BOOT 固件升级成功 | 成功 |
| 17 | 固件不匹配 | **用了错误的固件文件** |
| 36 (`0x24`) | OTA 升级冲突 | 另一路 OTA 正在进行 |

### OTA 错误代码（DTU 状态查询用）

| 码 | 含义 |
|---|---|
| 0 | 无错误 |
| 1 | 未知错误 |
| 2 | 网络异常 |
| 3 | 固件不匹配 |
| 4 | 存储失败 |

### 常见失败原因

| 现象 | 可能原因 |
|---|---|
| 请求阶段就失败 | 固件长度或校验和错误；固件与设备型号不匹配 |
| 传输中途超时 | BLE 信号弱、数据包发送过快（降低 transmissionRate） |
| 升级到一半断开 | 供电不足（升级期间电流较大）；蓝牙距离过远 |
| 升级后版本号未变 | 未触发写入（忘了发 `0x0CF1`）；或升级包被缓存但未执行 |
| 「固件不匹配」 | Boot 与 APP 固件配错；机型不符 |

## 12.7 实战要点

| 要点 | 说明 |
|---|---|
| **升级前务必读版本** | 固件必须与硬件/软件版本匹配，否则可能变砖 |
| **升级期间停轮询** | App 会暂停实时数据请求（`realTimeDataController.stop()`） |
| **一包一应答** | 不要连续盲发，必须等应答（或严格按速率间隔） |
| **校验和是累加和** | 固件全部字节的 u32 累加，不是 CRC |
| **结束包长度为 0** | 长度 0 是「发送完毕」的信号 |
| **完成后等重启** | 设备重启期间会断连，需重新连接再校验版本 |
| **权限要求高** | 部分升级路径要求 5 级以上权限 |
| **供电要稳** | 建议升级期间外接充电器，避免电量不足中断 |

> ⚠ **风险提示**：固件升级是协议中最危险的操作。
> 自研客户端在未充分验证前，建议先在本机模拟器或备用设备上测试，
> 并确保能通过 Boot 模式恢复。
