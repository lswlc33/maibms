# 第 14 章 · 新旧版本差异

> **本章目标**：说清两代 App（旧版原生小程序 / 新版 uni-app）在协议实现上的差异，
> 给出兼容性建议。如果你要做的是一个「通用」客户端，这一章告诉你要按哪一版的规则来。

## 14.1 版本背景

| | 旧版 | 新版 |
|---|---|---|
| 小程序 AppID | `wx393ab17de9e49031` | `wxe7b6244f6461fc6c` |
| 框架 | 原生小程序 + Vant Weapp | uni-app（Vue2 编译产物） + firstui |
| 体积 / 文件数 | 2.5 MB / 448 个 | 8.4 MB / 802 个 |

> 上表文件数为**首次解包时的原始统计**（含空文件与 1 个工具垃圾文件）。
> 清理后本地实际为 443 / 791 个文件，差额即被删除的 4 个 + 11 个空文件与各自 1 个垃圾文件。
| 页面数 | 24 + 1 分包 | 1 + 47（8 个分包） |
| 协议实现位置 | `utils/helper.js`、`app.js`、各页面 | `sdk/api/`（协议 SDK v3.2.0） |
| 设备类型支持 | 仅 BMS | BMS / 充电器 / 显示器 / 电源 |
| 通信方式 | 仅 BLE | BLE + MQTT + TCP |

新版里有一个组件会主动把用户引导到新小程序（`navigateToMiniProgram`），说明两者是**同一厂商的新旧两代客户端**。

**关键结论**：两代**共用同一套 BLE 协议**（帧格式、CRC、功能码、参数地址全部一致），
新版是在旧版基础上的**扩展**，不是替换。绝大多数旧版能读的报文，新版读法相同。

## 14.2 差异总表

| 维度 | 旧版 | 新版 | 是否需要特殊处理 |
|---|---|---|---|
| 帧格式 | `7E A1 … AA 55` | 相同 + 支持自定义地址 / `C1` | 建议兼容 `A1`/`C1`/`A0` |
| CRC | 同（低字节在前） | 同 | 否 |
| BLE 通道 | 固定 FFE1 | FFE1 / FFF3+FFF4 / FFF5+FFF6 自动探测 | 建议实现探测 |
| MTU | 请求 80 | 请求 512 | 否（用 MTU−10 即可） |
| 单次写长度 | 安卓 20 / iOS 80 | MTU − 10 | 否 |
| 轮询 | 500 ms / 读 190 字节 | 500 ms / 读 245 字节 | 用 245 更全 |
| 单体电压高位 | 直接 ÷1000 | 先 `& 0x1FFF` | **按新版** |
| 扩展段字段 | 无 | 本次充电时长、充电器信息等 24 字节 | 按长度判断 |
| 均衡 4 字节 | 只当位图 | 主动均衡机型解析为结构体 | **需要机型判定** |
| 扩展帧 0xFE | 无 | 机型识别 + 扩展状态 | 建议解析 |
| 身份 ID 解码 | 十进制点分 | UTF-8 字符串 | 按新版 |
| 电池类型值 | 小整数编码 | `0xFAFx` 编码 | 两者都支持 |
| 参数写入 | 逐条 `22` | 由服务端模板驱动 | 等价，按旧版实现即可 |
| 采集芯片指令 | 无 | `59` / `70` 指令族 | 按需 |
| 从机数据 | 无 | `51` / 寄存器 `3800` | 按需 |
| 日志读取 | 有（`03`） | 有（`03`） | 一致 |
| 重启系统 | `51` 命令号 `9` | `57` + `restartSystem` | 优先试 `51/9` |
| 保存参数 | `51/07` | 相同，另分流出 `53/56/57` | 用 `51/07` |
| 响应合法性判定 | 无 | 必须 `7ea1`/`7ec1` 开头 + `aa55` 结尾 | 建议实现 |
| GPS | 轮询 `06` | 接收推送 `7ea11600` | 两者都支持 |

## 14.3 逐项详解

### ① 单体电压高 3 位（最容易踩坑）

```
旧版：voltage = u16 / 1000
新版：voltage = (u16 & 0x1FFF) / 1000     ← 正确做法
```

高 3 位（bit13~15）是状态标志，新版解析为 `bsErrSt` 数组。
**始终按新版处理**，否则带标志位的固件会读出 8.191 V 之类的假值。

### ② 均衡字段的双重语义

同 4 字节，取决于机型：

```python
if is_active_bal(bms_type, bms_model, active_bal):
    info = parse_active_bal(v, bms_type)      # 结构体
else:
    bits = [(v >> i) & 1 for i in range(32)]  # 位图
```

判定算法见 [第 13.7 节](13-位域与枚举字典.md#137-主动均衡机型判定)。
**不做判定直接当位图读，会让主动均衡机型的线阻/电流显示成莫名其妙的均衡串号。**

### ③ 扩展段字段（24 字节）

长度判断规则：

```
if len(data) > 106 + 2N + 2M:        # 超出核心段
    解析扩展段（相对 T0 偏移 78 起 24 字节）
```

新版对扩展段采用「**有就解析，不够就跳过**」的策略：
核心段（相对 T0 偏移 0 ~ 77）必读，然后检查剩余长度是否够 24 字节，
够则继续读本次充电时长、剩余时间、充电器信息等字段。

> 注意长度判断用的是**核心段结尾**（`106 + 2N + 2M`），
> 而不是「核心段 + 扩展段」（`130 + 2N + 2M`）。
> 搞反会导致扩展段永远读不到。

### ④ 响应合法性判定

新版对每条通知先做快速过滤：

```
合法 = 以 "7ea1" 或 "7ec1" 开头 且 以 "aa55" 结尾
```

好处：

- 挡住半包、噪声、错位数据
- 天然支持并机的第二台设备（`C1`）

建议实现同样的过滤，但**不要**把它当作 CRC 的替代 —— 它只是快速筛选，
仍需完整 CRC 校验。

### ⑤ 身份 ID 的两种解码

同一份数据：

```
字符串方式（新版）：data[2:] 按 UTF-8 解码 → "VG82856PP2J6YF6C3"
十进制点分（旧版）：每字节转十进制用 . 连接 → "97.86.71.56..."
```

两种都是「有效」的表示，**协议层面数据是相同的**。
对接时建议用字符串方式（更易读），需要与旧版界面一致时才用点分。

### ⑥ 重启命令

| | 命令 |
|---|---|
| 旧版 | `7E A1 51 09 00 00 XX XX AA 55` |
| 新版 | `57` + `restartSystem`（应答 `67`），界面提示「重启蓝牙」 |

新版这个命令实际是**重启蓝牙模块**（`publishMessageWaitByCharacteristicId`）。
若目标是重启整机，优先尝试 `51/9`。

### ⑦ 保存命令的分流

新版按目标设备拆成四条：

```
51/07  → 保存到 BMS（最常用，与旧版相同）
53/30  → 保存到 DTU
56/xx  → 保存到屏幕 / 应用配置
57/xx  → 保存到蓝牙模块
```

对接 BMS 参数时**只用 `51/07`**。

### ⑧ 新版的协议模板机制

新版把「命令名 → 命令码 + 数据类型 + 倍率」的定义放在服务端
（`getFormatProtocol` 接口下发），App 本地只保留自定义解析器。

对自研客户端的影响：

- **不需要**复刻模板机制
- 直接按本书的固定协议实现即可，行为与官方 App 等价
- 但要注意：若厂商后续用模板下发了新的命令，自研客户端不会自动支持

## 14.4 兼容性策略建议

如果你要写一个**通用**的对接程序，按下面的优先级实现：

### 必做（两代通吃）

1. 帧格式 + CRC16-Modbus（低字节在前）
2. 500 ms 轮询实时数据（请求 245 字节）
3. 实时数据解码：**屏蔽单体电压高 3 位**
4. 参数分块读取（[第 6.3 节](06-参数读写.md#63-常用读取块)）
5. 参数单点写入 + `51/07` 保存
6. 权限校验（`23`）
7. 控制命令（`51` 命令号表）

### 建议做（提升兼容性）

8. BLE 通道探测（FFE1 失败时切 FFF3/FFF4、FFF5/FFF6）
9. 组合帧拆分（处理 `0x11` + `0xFE`）
10. 机型识别与主动均衡判定
11. 响应合法性判定（`7ea1`/`7ec1` 开头）

### 按需做

12. 日志读取（`03`）
13. 固件升级（`51`/`52`，或 `57` BLE 升级）
14. AFE 指令（`59`/`70`）
15. DTU 命令（`53`）
16. 从机数据（寄存器 `3800`）

### 关键实现原则

| 原则 | 说明 |
|---|---|
| **按长度保护** | 每个字段解析前判断剩余长度，不要越界 |
| **按 N/M 算偏移** | 永远先读串数与温度数，再算偏移 |
| **以新版规则为准** | 新版是旧版的超集，且修正了旧版的 bug |
| **保留原始报文** | 便于诊断；新版就把异常报文存入 `abnormalList` |
| **版本探测** | 连接后读一次版本（参数 620），据此决定是否解析扩展段 |

## 14.5 附：如何判断设备固件属于哪一代

按下面的顺序探测即可，无需用户干预：

```
① 读实时数据（245 字节）
② 看响应长度：
     ≤ 106 + 2N + 2M  →  旧固件，无扩展段
     > 106 + 2N + 2M  →  新固件，有扩展段（24 字节）
③ 看是否收到组合帧第二段（0xFE）：
     有  →  支持机型识别与扩展字段
     无  →  老固件
④ 读参数 620 的版本号字符串，记录到日志
⑤ 读参数 528 的 Boot 版本号，判断是否支持 OTA
```

这样你的客户端就能自适应地选择解析路径，而不是硬编码某一代的假设。
