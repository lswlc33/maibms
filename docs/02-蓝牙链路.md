## 2.1 设备发现与广播解析

> 🟠 **实测部分验证**（2026-09-29 同上）：实测能按名称前缀 `ANT` 扫到设备（`ANT@BLE24CBUB-3547`，RSSI −87 dBm 量级）；**广播字节内容的解析未验证**。

### 按名称识别（基础方式）

BMS 的蓝牙名以 **`ANT`** 开头（不区分大小写）：

```javascript
name.toUpperCase().startsWith("ANT")   // 旧版判定条件
```

扫描时过滤出这类设备即可。旧版扫描 2 秒后自动停止（`SCANTIME = 2000`）。

### 按广播数据识别（精确方式）

广播数据里带厂商自定义段，可解析出 **MAC、设备类型、配对码、连接数上限**。

**旧版**取第 4~9 字节作为 MAC：

```
advertisData.slice(4, 10) → "AA:BB:CC:DD:EE:FF"（大写）
```

**新版**的完整解析规则（`AdvertisingAnalyze.parse`）：若广播以 `FFFF` 开头，
剥离前两字节后按下列偏移解析（偏移相对剥离后的数据）：

| 偏移 | 长度 | 字段 | 解码 |
|---|---|---|---|
| 0 | 2 | 设备类型 | **两个字节互换**后查表（`byte1 byte0`） |
| 2 | 6 | MAC 地址 | 长度 ≥16 且 ≠20 时取此处 |
| 4 | 6 | MAC 地址（备用） | 其他长度时取此处，其中第 4 个字节 **+1** 修正 |
| 8 | 2 | 屏幕配对码 | 原样 |
| 10 | 2 | 充电器配对码 | 原样 |
| 12 | 1 | 最大可连接数 / 已连接数 | **高半字节 = 最大可连接数，低半字节 = 已连接数**（同一字节） |

> 最后一项容易看错：源码写作 `parseInt(r.slice(24,25),16)` 与 `parseInt(r.slice(25,26),16)`，
> 取的是**同一个字节的高、低两个半字节**，而不是相邻两个字节。

设备类型查表（注意是**高低字节互换后**的值）：

| 值 | 类型 |
|---|---|
| `0x056C` | BMS |
| `0x056D` | 屏幕（显示器） |
| `0x056E` | 充电器 |
| `0x056F` | DTU |

> 实战意义：知道了类型就能在扫描列表里区分 BMS、充电器、屏幕；
> 知道了 MAC 就能在广播里直接锁定目标设备（新版据此实现「配对码快速连接」）。

## 2.2 通道（特征值）与自动探测

> ✅ **实测已验证**（2026-09-29 · 真板 `ANT@BLE24CBUB-3547`，固件 `24CBUB02-240623C`）：该机 `FFE0` 服务下的**写与通知都是 FFE1**，订阅后即可收发；FFF3-4 / FFF5-6 未用到。

### 服务与特征

服务 UUID 固定：

```
0000FFE0-0000-1000-8000-00805F9B34FB
```

但不同固件版本把「写」和「通知」放在**不同的特征值**上，因此有三组候选通道：

| 通道名 | 写特征 | 通知特征 | 说明 | 复用的物理接口 |
|---|---|---|---|---|
| `ffe1` | FFE1 | FFE1 | 默认通道，新旧固件都支持 ★ | 标准数据通信通道 |
| `fff3-fff4` | FFF3 | FFF4 | 备用 A | **共享蓝牙屏接口** |
| `fff5-fff6` | FFF5 | FFF6 | 备用 B | **共享充电器接口** |

> **最省事的做法**：直接按 `ffe1` 收发。绝大多数设备可用，这也是旧版 App 的唯一策略。
> 只有当 `ffe1` 收不到应答时，才需要按下面的流程探测备用通道。

> ⚠ **备用通道不是「多出来的第二条链路」**：三组通道是同一颗 BLE 模组上的三组特征值，
> 背后复用的是不同的物理接口 —— 备用 A 占用**蓝牙屏**那一路，备用 B 占用**充电器**那一路，
> 占用期间对方就没法与保护板通信，而且这两条通道**都不支持固件升级**。
> 详见本节末的「备用通道的代价」。

### 候选列表生成规则

```
检测「可写特征 FFF5 是否存在」：
  存在   →  候选 = [ffe1, fff3-fff4, fff5-fff6]   （该硬件才暴露备用通道）
  不存在 →  候选 = [ffe1]                        （只有默认通道）
切换后备队列 = 候选去掉 ffe1 （不存在可写 FFF5 时为空，自动轮切直接跳过）
```

源码依据（新版 `utils/bleChannelDiagnostics.js`）：`w = !存在可写 FFF5`；
探测候选 `k = w ? [ffe1] : [ffe1, fff3-fff4, fff5-fff6]`；
手动切换页列出的备用通道 `y = w ? [] : [fff3-fff4, fff5-fff6]`。
`utils/bleComApi.js` 的 `startBmsChannelDiagnosis` 在备用通道名为空时直接记一条
「设备不支持备用通道，跳过自动轮切」并**不启动**看门狗。

> 换句话说：**备用通道只存在于暴露了 `FFF3/FFF5` 那批特征值的硬件上**；
> 只提供 `FFE1` 的设备候选里只有默认通道，既不会列 A/B，也不会自动轮切。

### 探测流程

```
对每个候选通道：
  1. 订阅该通道的通知特征
  2. 发送探测帧：7E A1 01 00 00 F5 58 62 AA 55   （即"读实时数据 245 字节"）
  3. 等待应答，超时 8 秒
  4. 若收到以 7E 开头、功能码为 0x11 或 0x12 的报文 → 通道可用，锁定并返回
  5. 否则切下一个通道，间隔 200 ms
全部失败 → 提示"所有通道均无法通信，请断电重启蓝牙后重试"
```

探测帧就是普通的实时数据读取命令，见 [第 5 章](05-实时数据.md)。

### 运行时通道轮切

新版在运行中会监控实时数据是否连续。若中断，触发「通道轮切」：

- 维护 `channelSwitchDepth`（切换深度）计数器
- 切换期间置位**流量锁** `isBmsChannelDiagnosisTrafficBlocked`，屏蔽其他报文，避免干扰探测
- 每次切换尝试都有独立超时与失败原因记录（`probeNoAck` / `switchFailed` 等）
- 全部失败后向用户提示重启蓝牙

### 「通信通道」页与手动切换（新版 UI）

新版把这些策略做成了一个显式的「通信通道」卡片页（源码 `pages_Detail/components/footerNew.js`，
文案表 `mp-main-locales/index.js`）。两种进入方式：**自动通道检测**（运行中实时数据中断时
自动开始，逐条试通道并显示「第 n / 共 m」进度，检测期间卡片页自动打开）与**手动切换**（用户点通道卡片）。

每张通道卡片由「名称 + 通道标签 + 说明/警示 + 状态按钮」组成：

| 状态按钮 | 文案键 | 出现时机 |
|---|---|---|
| 使用中 | `bleChannelInUse` | 当前正在用的通道（`uiChannelName`） |
| 切换中 | `bleChannelSwitching` | 正在切往这条通道（`switching && switchingChannelName === 该通道`） |
| 点击切换 | `bleChannelClickSwitch` | 空闲且可切换的通道 |
| 检测中… / 等待检测 / 通信失败 / 不支持 | `bleChannelDetecting` / `bleChannelWaitingDetect` / `bleChannelCommunicationFailed` / `bleChannelUnsupported` | 自动检测进行中，或该通道被判定不可用 |

卡片上的标签直接由特征值拼出：默认通道是 `ffe1收发`（读写同一个特征），
备用 A 是 `fff3发-fff4收`，备用 B 是 `fff5发-fff6收`（拼装代码 `buildChannelOptions`）。

交互与约束（均为源码行为）：

- 页头写死一句 **「点击通道卡片即可切换，切换会中断当前通信」**（`bleChannelManualSwitchDesc`）；
  自动检测态换成「检测到当前通信异常，正在自动检测可用通道」（`bleChannelAutoDetectingDesc`）。
- **切换一定会断一次链路**：置流量锁（`isBmsChannelDiagnosisTrafficBlocked`）→ 等总线静默 →
  在新通道上重新订阅通知并重连；切换期间**实时数据轮询暂停**，成功后按 250 ms 间隔重启
  （事件的收发见 `bleRealtimeSuspendRequest` / `bleRealtimeResumeRequest`）。
- 点到当前通道时只提示「当前已是 + 通道名」（`bleChannelAlreadyCurrent`；这条 toast 里 `ffe1`
  写作「标准通道」，A/B 写作「备用通道 A / B」），不发任何报文。
- **备用通道只在支持它的硬件上出现**：设备**没有**可写特征 `FFF5` 时，候选通道只有 `ffe1`，
  通道页不列 A/B，自动轮切也直接跳过（`getManualChannelNames()` 返回空列表，
  并记一条「设备不支持备用通道」）。
- 全部通道都失败时提示「所有通道均无法通信」+「请断电重启蓝牙后重试」，
  并给出「返回设备列表 / 重新检测」两个动作。
- 失败原因会被翻译成中文再显示（`normalizeReason`）：

| 源码 reason | 界面文案 |
|---|---|
| `realtimeTimeout` / `probeNoAck` / `switchFailed` / `allChannelsNoRealtime` | 未收到设备响应 |
| `applyChannelMissing` | 通道切换能力不可用 |
| `ffe1Unsupported` | 连接超时 |
| `channelNotFound` | 通道不可用 |
| `busy` | 通道被占用 |
| `sessionEnded` | 检测已结束 |
| 其它 | 通信异常 |

还有一条与通道相关的兜底分支：检测到**设备通讯地址被修改**时提示「设备通讯地址异常」，
引导用户去「更多」页执行「恢复通讯地址」后再通信（`bleChannelAddressBrokenTitle` / `...Desc`）。

> 源码里另有两个已定义但本次未启用的键：`bleChannelPriorityDirect`（「优先直连」）与
> `bleChannelDefaultUnsupportedDesc`（「当前设备不支持标准数据通信通道」），其触发条件源码未见明确判据。

> 本项目客户端按同一套策略实现：连接时逐条候选发探测帧、运行中失联按顺序轮切，
> 并在「设置 → 通信通道」提供同名卡片页（当前通道 / 手动切换 / 按设备记住选择）。

### 备用通道的代价：接口共享与升级限制

新版给两个备用通道各挂了一条橙色警示（文案直接来自源码）：

| 通道 | 官方警示 | 来源键 |
|---|---|---|
| 备用 A `fff3-fff4` | 使用期间蚂蚁蓝牙屏将无法与保护板通信,不支持固件升级 | `bleChannelScreenUnavailable` + `bleChannelUnsupported` + `info.UPGRADE` |
| 备用 B `fff5-fff6` | 使用期间蚂蚁充电器将无法与保护板通信,不支持固件升级 | `bleChannelChargerUnavailable` + 同上 |

同族还有两个更直白的标签键：`共享蓝牙屏接口`（`bleChannelSharedScreen`）与
`共享充电器接口`（`bleChannelSharedCharger`）—— 这正是两条通道的物理含义
（这两个键在本次解包的卡片模板里没有被渲染，卡片上显示的是上表的警示句）。

由此有两条实现上的硬约束：

1. **备用通道是临时救急，不是更快的第二条链路**。它占了蓝牙屏 / 充电器的接口，用户的外设就会掉线，
   所以默认通道恢复后应尽快切回 `ffe1`（新版的手动切换页就是为这个场景准备的）。
2. **非默认通道不开放升级**。新版的 BMS 固件升级与采集芯片（AFE）升级入口都先判当前通道：

    ```
    当前 BLE 通道 === "ffe1"  →  正常进入升级
    否则                      →  只弹「当前蓝牙通道不支持升级，请切换到默认通道」并中止
    ```

   源码位置：`pages_Detail/controlComponents/bmsControl.js` 的 `handleBmsUpgrade` 与
   `showCollectChipFun`（文案键 `updateErrorDesc`）。协议侧见 [第 12.1 节](12-固件升级.md#121-升级对象与功能码)。

### 应答合法性判定

新版对接到的每条通知都做一次快速判定：

```
合法 = 以 "7ea1" 或 "7ec1" 开头  且  以 "aa55" 结尾
```

不满足的报文被丢进 `abnormalList`（异常报文列表，用于诊断）。
这套判定同时让 `7EC1` 开头的帧被当作实时数据处理 —— 该地址的具体含义源码未说明，
推测为总线上的另一台设备，详见 [第 3.1 节](03-帧格式与校验.md#31-帧结构)。

## 2.3 MTU 与分包

> 🟠 **实测部分验证**（2026-09-29 同上）：实测「请求 MTU 512 → 按 MTU−10 分片（封顶 240 字节）」可正常收发；实际协商到的 MTU 数值未逐次记录。

BLE 单次写入的字节数受 MTU 限制，两代实现不同：

| | 旧版 | 新版 |
|---|---|---|
| 请求 MTU | 80（连接后 1 秒调用 `setBLEMTU`） | 512（Android 最多重试 3 次；iOS 不设置） |
| 单次写长度 | 安卓 **20** 字节 / iOS **80** 字节 | `MTU − 10`（未协商时按 20 算，即 10 字节） |
| 写间隔 | 10 ms（发送队列定时器） | `sendMsgInterval` 节流参数 |

### 分片与重组

协议本身**没有分片机制** —— 一次写入的数据就是一条完整报文（或组合帧）。
如果一条报文超过单次写长度，必须由 App 切成多次写入：

```
一条 200 字节的应答 → App 切成 20 次 10 字节写入
BMS 侧收到的多片 → 按时间顺序拼进缓冲区 → 从缓冲区里找 7E ... AA 55
```

这解释了为什么旧版要维护 `BUF_RECEIVE`（1024 字节环形缓冲）和逐字节滑动查找帧头的逻辑：
**接收侧必须自己处理粘包与断包**，协议帧定界完全依赖 `7E A1` 头与 `AA 55` 尾。

> **实现建议**：接收端维护一个字节流缓冲区，每次收到通知就追加，然后循环执行
> 「找帧头 → 判断帧类型 → 算帧长 → 校验 CRC → 取出报文」直到缓冲区剩余不足一帧。

## 2.4 轮询节奏与心跳

> 🟠 **实测部分验证**（2026-09-29 同上）：实测以 **900 ms 间隔 / 700 ms 超时** 轮询稳定（弱信号 −87 dBm 下）；文档建议的 500 ms 未实测。

**BMS 不主动推送实时数据**，必须轮询：

| | 旧版 | 新版 |
|---|---|---|
| 周期 | 500 ms | 500 ms（`useRealTimeData` 默认值） |
| 报文 | `7E A1 01 00 00 BE 18 55 AA 55`（读 190 字节） | `7E A1 01 00 00 F5 58 62 AA 55`（读 245 字节） |
| 启动条件 | 已连接 + 通知订阅成功 | 设备连接状态正常 + 无升级/日志中断标志 |

新版在以下场景会**暂停轮询**（`realTimeDataController.stop()`），事后再恢复：

| 场景 | 源码位置 |
|---|---|
| 读写参数期间（`setParamsApi` 前后成对调用） | `mixJs/bleComApi.js` |
| 权限弹窗打开时 | `comPop/permissionspop.js`、`permissionspopBox.js`、`modepop.js` |
| 固件升级期间 | `components/bmsAndBoot.js` |

原因很简单：这些操作需要独占总线，轮询报文会挤占响应窗口，造成应答错乱。

> **注意**：**读取日志（`0x03`）并没有暂停轮询** —— 日志应答有独立功能码 `0x13`
> 和回显的日志序号，可以和轮询共存，不需要互斥。

> **实现建议**：自己也照此设计 —— 任何「发起一次命令并等待应答」的操作，
> 先停轮询，拿到应答后再恢复，否则很容易把轮询的应答误当成命令的应答。

## 2.5 连接建立时序

> ✅ **实测已验证**（2026-09-29 · 真板 `ANT@BLE24CBUB-3547`，固件 `24CBUB02-240623C`）：「先订阅通知再发命令」实测有效；首次订阅（CCCD 写入）后才开始轮询。

完整的连接过程：

```
① 初始化蓝牙适配器（openBluetoothAdapter）
      失败 errCode 10001 → 蓝牙未打开

② 扫描（startBluetoothDevicesDiscovery）
      过滤名称以 ANT 开头，或解析广播取目标 MAC

③ 连接（createBLEConnection）
      停止扫描 → 建连

④ 获取服务（getBLEDeviceServices）
      找到 FFE0

⑤ 获取特征（getBLEDeviceCharacteristics）
      找通知特征与写特征（或按 §2.2 探测）

⑥ 订阅通知（notifyBLECharacteristicValueChange, state=true）
      注册 onBLECharacteristicValueChange 回调
      ★ 必须订阅成功后才可能收到任何应答

⑦ 设置 MTU（setBLEMTU）
      旧版 80；新版 512（Android）

⑧ 握手
      测权限：读实时数据，看"当前权限"字节
      若权限 < 1 → 发密码校验：7E A1 23 4A 01 08 <8字节ASCII密码> CRC AA 55
      读版本：7E A1 02 6C 02 20 58 C4 AA 55
      读 ID ：7E A1 04 00 00 0C 98 EC AA 55

⑨ 启动轮询（每 500 ms 发实时数据读取）
```

关键顺序点：**先订阅通知，再发命令**。反了就会「命令发出去了但没有应答」。

## 2.6 断连与重连

> ✅ **实测已验证**（2026-09-29 · 真板 `ANT@BLE24CBUB-3547`，固件 `24CBUB02-240623C`）：实测断开（关蓝牙）后自动重连并恢复数据与权限；重连需要「停扫描 → 等静默 → 直连重试 → 等待式连接」的组合，见 [15.4 节](15-实战与调试指南.md#154-常见陷阱与排查)。

- 旧版维护 **12 个**连接状态常量（`utils/constants.js`，编号 0~4、6~12）：

| 值 | 常量 | 含义 |
|---|---|---|
| 0 | STATE_DISCONNECTED | 已断开 |
| 1 / 2 | STATE_SCANNING / SCANNED | 扫描中 / 已停止扫描 |
| 3 / 4 | STATE_CONNECTING / CONNECTED | 连接中 / 已连接 |
| 6 | STATE_CONNECTING_ERROR | 连接失败 |
| 7 / 8 | STATE_NOTIFY_SUCCESS / NOTIFY_FAIL | 通知订阅成功 / 失败 |
| 9 | STATE_CLOSE_BLE | 蓝牙未打开 |
| 10 / 11 | STATE_NOTBLE_SYSTEM_VERSION / WCHAT_VERSION | 系统版本过低 / 微信版本过低 |
| 12 | STATE_INIT_SUCCESS | 适配器初始化成功 |

> 编号没有 5 —— 这一点在设计自己的状态机时要注意（可直接照抄这套编号，便于与日志对照）。
- 新版有自动重连（`addAutoReconnect`），连接成功回调状态码 `2500` 视为成功。
- **断连后必须重新订阅通知**，并重新握手（权限会丢失，需要重新校验密码）。
- 新版会记录「静默重连」（`silentChannelReconnect`）与「静默升级」状态，用于升级过程中不让用户察觉。

> **权限会因断连丢失** —— 这是实际开发中常见的坑：重连后直接写参数会返回「权限不足」，
> 需要重新发送密码校验帧。详见 [第 9 章](09-权限与身份.md)。

## 2.7 哨兵模式：BLE 当作云端透传通道

新版有一个「哨兵模式」（`utils/sentinelManager.js`），它把手机变成**云端的 BLE 网关**：

```
云端 --MQTT--> App --BLE--> BMS
云端 <--MQTT-- App <--BLE-- BMS
```

工作方式（源码 `handleRawBleMessage` / `waitBleReplyAndPublish`）：

```
① 云端下发一段**原始十六进制帧**（不是命令名）
② App 用 bleComApi.publishMessage(hex, "", "sentinel") 原样写入 BLE
③ 记录 `帧的第 5~10 个十六进制字符`（= 功能码 + 寄存器两字节）作为应答匹配键
④ 收到通知后按该键派发事件 `sentinelBle<功能码+寄存器>`
⑤ 把应答**原文**通过 MQTT 上报云端
```

要点：

| 项 | 说明 |
|---|---|
| 帧格式 | 与本地会话**完全一致**（`7E…AA55`），云端只需按本书的帧规则构帧 |
| 匹配方式 | 按「功能码 + 寄存器」匹配，不校验序号，因此同一命令的多次应答都可被捕获 |
| 特定路由 | `7ea11600`（GPS 推送）等帧被单独识别并转给哨兵处理，见 [第 10.2 节](10-DTU与GPS.md#102-gps-定位数据0x06--0x16) |
| 对自研客户端的含义 | 帧内容由云端生成，**离线源码里看不到要发什么**；若要复刻哨兵功能，需要与云端协议配合 |
| 前提 | App 需保持 BLE 连接（或可被唤醒重连），并保存 `sentinelBle`（设备 antId）用于标识 |

> 换句话说：设备能被「远程读写」，靠的不是 BMS 自己联网，而是**手机在中间转发 BLE 帧**。
> 这也是为什么新版既支持直连 BLE，又支持 MQTT —— 两条路径最终操作的是同一套帧。
