## 15.1 抓包方法

### 方法一：Android HCI 日志（推荐，免费）

```
① 手机开启开发者选项
② 打开"启用蓝牙 HCI 信息收集日志"
③ 用官方 App 连接 BMS 操作几分钟
④ 抓日志：
     adb bugreport  →  解压 bugreport-*.zip
     取出 /FS/data/misc/bluetooth/logs/btsnoop_hci.log
⑤ 用 Wireshark 打开该文件，过滤：
     btatt.opcode == 0x52 || btatt.opcode == 0x1b     （写/通知）
```

Wireshark 里 ATT 层的 Value 字段就是从 App 到 BMS 的原始字节。

### 方法二：nRF Connect（交互式，适合手动试）

```
① 安装 nRF Connect
② 扫描 → 找到名称以 ANT 开头的设备 → 连接
③ 展开服务 0000FFE0-...
④ 打开 FFE1 的 Notify（点三个箭头图标）
⑤ 在 FFE1 的 Write 里输入十六进制报文并发送
⑥ 观察 Notify 收到的应答
```

**第一条命令建议先发** `7EA1010000F55862AA55`（读实时数据），
能收到 `7EA11100...` 就说明协议通了。

### 方法三：iOS PacketLogger / Xcode

iOS 抓 BLE 比较麻烦，需要 PacketLogger（Apple 开发者工具）+ 蓝牙日志描述文件。
若只需观察，用 Android 更省事。

### 方法四：硬件嗅探器

nRF Sniffer（配合 Wireshark）、Ellisys 等专用设备。
优点是能看到连接建立过程与广播包，缺点是成本高。

## 15.2 五步识别一条报文

拿到一串字节，按下面五步走：

### 第 1 步：确认这是不是协议帧

```
检查开头 1 字节：7E ?
检查结尾 2 字节：AA 55 ?
   ✗ → 可能是半包、噪声，或组合帧的第二段（见第 5 步）
   ✓ → 继续
```

### 第 2 步：读地址与功能码

```
字节 1 = 地址     A1 = BMS 主机 / C1 = 第二台设备 / A0 = 采集芯片
字节 2 = 功能码
```

### 第 3 步：按功能码判断帧型

```
功能码 < 0x10  →  短帧，帧长固定 10 字节，长度字段 = 请求字节数
功能码 ≥ 0x10  →  长帧，帧长 = 10 + 长度字段
```

### 第 4 步：查功能码表定位章节

```
11 → 实时数据   （第 5 章）
12 → 参数数据   （第 6 章）
13 → 事件日志   （第 8 章）
14 → 身份 ID    （第 9 章）
16 → GPS        （第 10 章）
17 → GPRS 配置  （第 10 章）
42 → 写参数结果 （第 6 章）
43 → 权限结果   （第 9 章）
61 → 控制结果 / 从机数据（第 7 章）
63 → DTU 结果   （第 10 章）
69 → AFE 应答   （第 11 章）
80 → AFE 扩展应答（第 11 章）
FE → 扩展信息 / 机型（第 11 章）
```

### 第 5 步：检查有没有第二段

**长帧解析完后，若剩余字节还能构成一段**（功能码 ≥ 0x10 起步），
说明是组合帧，继续按第二段规则解析（[第 3.3 节](03-帧格式与校验.md#33-组合帧)）。

### 完整示例

```
7E A1 11 00 00 AA 05 01 04 10 ... AA 55
│  │  │  └┬┘ └┬┘ └┬┘
│  │  │   │   │   └── 数据区 0xAA = 170 字节
│  │  │   │   └────── 长度字段
│  │  │   └────────── 寄存器 0（实时数据固定为 0）
│  │  └────────────── 功能码 0x11 = 实时数据
│  └───────────────── 地址 A1 = BMS 主机
└──────────────────── 帧头

数据区首个字节 05 → 权限 5
第二字节   01 → 电池状态 = 静止
第三字节   04 → 温度数 M = 4
第四字节   10 → 串数 N = 16

长度校验：N=16, M=4
  核心版 = 106 + 2×16 + 2×4 = 146
  完整版 = 130 + 2×16 + 2×4 = 170
  实际长度 170 = 完整版 → 该固件带扩展段
```

> 上面演示了「用长度反推固件能力」：长度只到 146 就是旧固件（无扩展段），
> 到 170 就是新固件。任何介于两者之间的长度都是异常，应当丢弃并记日志。

## 15.3 最小实现清单

按顺序实现，每完成一步都能验证：

### 阶段一：连上并读到数据

- [ ] 扫描并过滤名称以 `ANT` 开头的设备
- [ ] 连接、发现服务 `FFE0`、找到 `FFE1` 的写与通知特征
- [ ] 订阅通知（`notifyBLECharacteristicValueChange`）
- [ ] 发送 `7EA1010000F55862AA55`，收到 `7E A1 11 ...` 应答
- [ ] 实现帧缓冲区 + 帧头查找 + CRC 校验
- [ ] **里程碑**：稳定收到实时数据

### 阶段二：正确解码

- [ ] 读 N（数据[3]）与 M（数据[2]），按公式算偏移
- [ ] 解码单体电压（`& 0x1FFF` ÷1000）、温度（s16）
- [ ] 解码总压、电流、SOC、SOH
- [ ] 解码保护位 / 告警位（64 位位域）
- [ ] **里程碑**：界面显示与官方 App 一致的电压/电流/SOC

### 阶段三：参数读写

- [ ] 分块读参数（先试 152 起 142 字节）
- [ ] 单点写参数（`22`）+ 解析 `42` 结果码
- [ ] 保存（`51/07`）
- [ ] **里程碑**：改一个阈值 → 保存 → 回读确认

### 阶段四：权限与控制

- [ ] 读实时数据看权限值
- [ ] 密码校验（`23`）
- [ ] 控制命令（开/关 MOS、均衡、蜂鸣器）
- [ ] **里程碑**：能远程开关充电 MOS

### 阶段五：进阶

- [ ] 组合帧拆分（`0x11` + `0xFE`）
- [ ] 机型识别与主动均衡解析
- [ ] 日志读取（`03`）
- [ ] 通道探测与故障切换
- [ ] 固件升级

## 15.4 常见陷阱与排查

### 通信类

| 现象 | 原因 | 排查 |
|---|---|---|
| 发命令没有应答 | 没订阅通知就发命令 | 先订阅再发 |
| 前几条命令正常，后面全无响应 | 违反「命令间隔」；设备处理不过来 | 命令之间留 200 ms 以上；一次只等一个应答 |
| 收到的数据是乱码 | 粘包/断包处理不当 | 用缓冲区 + 帧头查找，不要假设一次通知就是一帧 |
| CRC 一直校验失败 | 覆盖范围错；字节序错 | 短帧覆盖 `[1..5]`，长帧 `[1..5+N]`；CRC 低字节在前 |
| 读参数返回全 0 | 权限不足 | 先做密码校验 |
| 偶发丢数据 | 轮询期间操作 | 操作前停轮询，完成后再启动 |

### 解码类

| 现象 | 原因 | 排查 |
|---|---|---|
| 单体电压 8.191 V 之类 | 未屏蔽高 3 位 | `& 0x1FFF` |
| 温度 65000 多 | 当无符号读了 | 按 s16 读 |
| 电压/电流错位 | 没用 N/M 算偏移 | 先读数据[2]、数据[3] |
| SOC 显示 65535 | 偏移错 | 检查是否把某 4 字节字段当 2 字节读 |
| 均衡状态和实际不符 | 未做主动均衡判定 | 按 [13.7 节](13-位域与枚举字典.md#137-主动均衡机型判定) |
| 电池类型显示空 | 值不是 `0xFAFx` | 检查是否用小整数编码 |
| 把 `0x42` 首字节当结果码 | 误解题意 | `0x42` = 参数回显；失败码在 `0xFF` 附加段 |
| 写失败却查不到原因 | 漏解析同一帧的第二段 | 组合帧必须拆两段（[第 3.3 节](03-帧格式与校验.md#33-组合帧)） |

### 操作类

| 现象 | 原因 | 排查 |
|---|---|---|
| 写了参数但重启后恢复 | 没发保存命令 | 发 `51/07` |
| 保存后仍不生效 | 保存了但值超范围被拒 | 看 `0xFF` 附加段的结果码（2/3） |
| 改参数返回「大于最大值」 | 值超范围 | `0xFF` 附加段里带回参数地址与允许的上限 |
| 关闭蓝牙后连不上 | 发了 `51/28`（蓝牙关闭） | 需通过其他方式唤醒（充电/按键） |
| 电流归零后数值异常 | 归零时电池有电流 | 必须在无电流状态下执行 |
| 权限突然失效 | 断连/重启后权限丢失 | 重连后重新校验密码 |

### 蓝牙连接类（Android 实测，2026-09-29）

| 现象 | 原因 | 对策 |
|---|---|---|
| `connectGatt` 返回成功但立刻断开（HCI `0x08`） | 弱信号或链路未收干净 | 停扫描后**等 450 ms** 再建链；失败按 1/2/4/8 s 退避重试 |
| 建链失败 `0x3E`（Conn Failed to Establishment） | 信号弱、或刚扫完就直连 | 直连重试若干次后改用**等待式连接**（Android `autoConnect=true`），实测正是靠它建上的 |
| 重试时旧连接的回调把新连接判死 | 上一次 GATT 的迟到回调 | 回调里先判 `g == 当前 gatt`，不是就 `close()` 丢掉 |
| 扫描结束后仍连不上 | 扫描未真正停止 | `stopScan()` 与 `connectGatt` 之间留间隔 |
| 弱信号下 `0x43` 应答 >2 s 才回 | 链路重传 | 命令超时给到 4 s（轮询读取 700 ms 够用） |
| 扫描界面永远停「正在搜索」 | 没有扫描窗口 | 设 15~20 s 窗口，到点自动停并显示「未发现设备」+ 重新扫描 |
| 命令收下上一条的应答 | 只比对功能码 | **功能码 + 寄存器**都要比对 |
| 分片写入丢包 | 分片超过从机承受上限 | 按 MTU−10 分片并**封顶 240 字节**，片间隔 10~12 ms |

> 服务与通道（该机型）：服务 `1800 / 1801 / FFE0`，**写与通知都是 FFE1**；先订阅通知再发命令。

### 权限与界面呈现类（实测教训）

| 现象 | 原因 | 对策 |
|---|---|---|
| 密码校验「成功」却仍被拒 | `0x43` 回的是当前权限，失败不回 0 | 判定用 `返回值 ≥ 所校验等级`（见 [9.3 节](09-权限与身份.md#93-权限应答与状态跟踪)） |
| 参数区读出满屏 `65535` | 权限不足时整块回 `0xFFFF` | 视为「未获授权」显示 `--`；保护参数区实测需 ≥2 级 |
| 界面把 `0xFFFF` 当温度显示成 65534 ℃ | 缺 s16 / 未披露判定 | 温度按 s16；`0xFFFF` 一律 `--` |
| 断连后指标变 `--`、容量列还是旧值 | 两套判据不一致 | 统一：**从未收到数据**全 `--`；**连过再断**保留最后值并在横幅标注「断开前最后数据」 |
| 深色主题下电池卡文字看不清 | 白字压在了亮色填充上 | 卡内文字按填充色亮度取前景；填充不足半卡时用常规前景色 |
| 未连接时按钮点了只吃「权限不足」 | 没做前置态判断 | 未连接就置灰控制按钮并说明原因；权限不足与未连接要分开提示 |

### 危险操作预警

| 操作 | 风险 |
|---|---|
| `51/11` 关闭系统 | 断电关机，需外部唤醒 |
| `51/12` 恢复出厂设置 | 所有参数回到默认 |
| `51/42` 恢复厂家设置 | 更彻底，可能丢失标定 |
| `51/28` 蓝牙关闭 | 蓝牙断开后无法再连 |
| `51/37` 清零保护次数 | 历史数据丢失 |
| `22` 写保护阈值 | 设错会导致误保护或失去保护 |
| 固件升级 | 变砖风险，务必确认固件匹配 |

> ⚠ **强烈建议**：所有危险操作前先读取并保存一份完整参数备份（参数区 0~786），
> 出问题可逐项恢复。

## 15.5 参考实现（Python）

一个可直接运行的最小实现骨架（假设你已有一个 BLE 传输层对象 `ble`，
提供 `write(bytes)` 与回调 `on_notify(bytes)`）：

```python
"""蚂蚁 BMS 蓝牙协议最小实现参考"""

# ---------- CRC ----------
def crc16_modbus(data: bytes) -> int:
    crc = 0xFFFF
    for b in data:
        crc ^= b
        for _ in range(8):
            crc = (crc >> 1) ^ 0xA001 if crc & 1 else crc >> 1
    return crc


# ---------- 组帧 ----------
def build(addr: int, func: int, reg: int, data: bytes = b"",
          length: int = None) -> bytes:
    """length 为 None 时用 len(data)（长帧）；读命令需显式传请求字节数"""
    n = len(data) if length is None else length
    body = bytes([addr, func, reg & 0xFF, (reg >> 8) & 0xFF, n]) + data
    crc = crc16_modbus(body)
    return b"\x7E" + body + bytes([crc & 0xFF, crc >> 8]) + b"\xAA\x55"


def read_realtime(addr=0xA1) -> bytes:
    return build(addr, 0x01, 0x0000, b"", length=0xF5)

def read_params(start: int, count: int, addr=0xA1) -> bytes:
    return build(addr, 0x02, start, b"", length=count)

def write_param(reg: int, raw_u16: int, addr=0xA1) -> bytes:
    return build(addr, 0x22, reg, bytes([raw_u16 & 0xFF, raw_u16 >> 8]))

def control(cmd: int, addr=0xA1) -> bytes:
    return build(addr, 0x51, cmd, b"")

def auth(password: str, level_addr: int = 330, addr=0xA1) -> bytes:
    pwd = password.encode()[:8].ljust(8, b"\x00")
    return build(addr, 0x23, level_addr, pwd)


# ---------- 解帧 ----------
def _payload_and_crc(buf: bytearray, func: int, n: int):
    """返回 (payload, crc_bytes, seg_total) —— seg_total 含帧尾 AA55"""
    if func < 0x10:                       # 短帧：固定 10 字节，无数据区
        return bytes(buf[1:6]), bytes(buf[6:8]), 10
    # 长帧：6(头) + n(数据) + 2(CRC) + 2(尾)
    return (bytes(buf[1:6 + n]), bytes(buf[6 + n:8 + n]), 10 + n)


def _crc_ok(payload: bytes, crc_bytes: bytes) -> bool:
    return crc16_modbus(payload) == (crc_bytes[0] | crc_bytes[1] << 8)


def parse_frames(buf: bytearray, max_buf: int = 4096):
    """
    从流缓冲区中抽取完整报文，返回 [(func, reg, data, is_seg2), ...]

    支持：短帧 / 长帧 / 组合帧（首段 + 无帧头的第二段）
    注意：组合帧的 AA 55 只在整条报文末尾出现一次，
          所以首段末尾那两字节不是帧尾 —— 必须靠 CRC + 后续结构判断。
          数据不足时要 break 等数据，绝不能滑动丢弃。
    """
    out = []
    while True:
        i = buf.find(b"\x7E")
        if i < 0:
            buf.clear(); break
        if i:
            del buf[:i]
        if len(buf) < 6:
            break

        func, n = buf[2], buf[5]
        payload, crc_bytes, seg_total = _payload_and_crc(buf, func, n)

        if len(buf) < seg_total:                       # 首段还没收全
            if len(buf) > max_buf:                     # 防御：异常数据堆积
                del buf[:1]
                continue
            break

        if not _crc_ok(payload, crc_bytes):
            del buf[:1]                                # CRC 失败 → 滑动重找
            continue

        reg = buf[3] | (buf[4] << 8)
        data = b"" if func < 0x10 else bytes(buf[6:6 + n])
        tail_at = seg_total - 2                        # 帧尾本应出现的位置

        # 情况 A：首段自带帧尾 → 单段报文
        if buf[tail_at:tail_at + 2] == b"\xAA\x55":
            out.append((func, reg, data, False))
            del buf[:seg_total]
            continue

        # 情况 B：后续字节可能构成第二段（无帧头）
        if len(buf) < tail_at + 6:
            break                                      # 长度不足以判断 → 等数据

        f2 = buf[tail_at]
        if f2 < 0x10:                                  # 不是合法的段 → 结构错误
            del buf[:1]
            continue

        n2 = buf[tail_at + 3]
        seg2_total = 8 + n2                            # 4(字段) + n2 + 2(CRC) + 2(尾)
        if len(buf) < tail_at + seg2_total:
            if len(buf) > max_buf:
                del buf[:1]
                continue
            break                                      # 第二段还没收全 → 等数据

        p2 = bytes(buf[tail_at:tail_at + 4 + n2])
        c2 = bytes(buf[tail_at + 4 + n2:tail_at + 6 + n2])
        t2 = buf[tail_at + seg2_total - 2:tail_at + seg2_total]
        if _crc_ok(p2, c2) and t2 == b"\xAA\x55":
            reg2 = buf[tail_at + 1] | (buf[tail_at + 2] << 8)
            out.append((func, reg, data, False))
            out.append((f2, reg2,
                        bytes(buf[tail_at + 4:tail_at + 4 + n2]), True))
            del buf[:tail_at + seg2_total]
            continue

        del buf[:1]                                    # 第二段校验失败 → 滑动重找
    return out


# ---------- 实时数据解码 ----------
def u16(d, i): return d[i] | d[i + 1] << 8
def s16(d, i): return (lambda v: v - 0x10000 if v >= 0x8000 else v)(u16(d, i))
def u32(d, i): return d[i] | d[i+1] << 8 | d[i+2] << 16 | d[i+3] << 24
def s32(d, i): return (lambda v: v - 2**32 if v >= 2**31 else v)(u32(d, i))

def decode_realtime(d: bytes) -> dict:
    """解码 0x11 数据区（d 从数据区第 0 字节开始）"""
    auth, state, M, N = d[0], d[1], d[2], d[3]
    protect = int.from_bytes(d[4:12], "little")
    warn = int.from_bytes(d[12:20], "little")

    p = 28
    cells = []
    for _ in range(N):
        cells.append(((u16(d, p) & 0x1FFF) / 1000.0, (d[p + 1] >> 5) & 7))
        p += 2
    temps = [s16(d, p + 2 * k) for k in range(M)]
    p += 2 * M

    t0 = p                                   # = 28 + 2N + 2M
    out = {
        "auth": auth, "state": state, "cellCount": N, "tempCount": M,
        "protectBits": [PROTECT_BITS[i] for i in range(64) if protect >> i & 1],
        "warnBits":    [WARN_BITS[i] for i in range(64) if warn >> i & 1],
        "cells": [c[0] for c in cells], "cellFlags": [c[1] for c in cells],
        "temps": temps,
        "mosTemp": s16(d, t0 + 0), "eqTemp": s16(d, t0 + 2),
        "totalVoltage":  u16(d, t0 + 4) / 100.0,
        "current":       s16(d, t0 + 6) / 10.0,
        "soc": u16(d, t0 + 8), "soh": u16(d, t0 + 10),
        "dischargeMos": d[t0 + 12], "chargeMos": d[t0 + 13],
        "eqState": d[t0 + 14], "bmsType": d[t0 + 15],
        "physicsAh": u32(d, t0 + 16) / 1e6,
        "surplusAh": u32(d, t0 + 20) / 1e6,
        "cycleAh":   u32(d, t0 + 24) / 1e3,
        "power": s32(d, t0 + 28), "runTimeMs": u32(d, t0 + 32),
        "eqFlag": u32(d, t0 + 36),
        "maxCell": (u16(d, t0 + 40) / 1000.0, u16(d, t0 + 42)),
        "minCell": (u16(d, t0 + 44) / 1000.0, u16(d, t0 + 46)),
        "cellDiff": u16(d, t0 + 48) / 1000.0,
        "cellAvg":  u16(d, t0 + 50) / 1000.0,
        "batteryType": u16(d, t0 + 60),
        "cumDischargeAh": u32(d, t0 + 62) / 1e3,
        "cumChargeAh":    u32(d, t0 + 66) / 1e3,
        "cumDischargeSec": u32(d, t0 + 70),
        "cumChargeSec":    u32(d, t0 + 74),
    }
    # 扩展段（可选，24 字节）
    if len(d) > 106 + 2 * N + 2 * M:
        out.update({
            "lastChargeSec":     u32(d, t0 + 78),
            "lastChargeGapSec":  u32(d, t0 + 82),
            "chargeRemainMin":   u16(d, t0 + 86),
            "dischargeRemainMin": u16(d, t0 + 88),
            "highSpeedCurrent":  s16(d, t0 + 90) / 10.0,
            "chargerOutV": u16(d, t0 + 96) / 10.0,
            "chargerOutA": u16(d, t0 + 98) / 10.0,
            "chargerState": u16(d, t0 + 100),
        })
    return out
```

## 15.6 自检向量

用下面这组「输入 → 期望输出」验证你的实现。
本节所有期望值均由**本仓库参考实现实测得出**（组帧 7 项、解帧 8 个场景、解码 11 个字段全部通过）。

### CRC 与组帧

| 输入 | 期望 |
|---|---|
| `crc16_modbus(bytes.fromhex("A1010000F5"))` | `0x6258` |
| `build(0xA1, 0x01, 0, b"", 0xF5).hex()` | `7ea1010000f55862aa55` |
| `build(0xA1, 0x02, 104, b"", 32).hex()` | `7ea1026800201865aa55` |
| `write_param(4, 3650).hex()` | `7ea122040002420e4c2caa55` |
| `control(6).hex()` | `7ea1510600006924aa55` |
| `control(7).hex()` | `7ea15107000038e4aa55` |
| `auth("12345678").hex()` | `7ea1234a01083132333435363738db50aa55` |

### 解帧（8 个场景）

把下面几条做成测试用例，能覆盖绝大多数流式解析的坑：

| # | 场景 | 期望 |
|---|---|---|
| 1 | 单段长帧（`0x11`，186 字节数据）整条喂入 | 解析出 1 段，缓冲区清空 |
| 2 | 组合帧（`0x11` + `0xFE`）整条喂入 | 解析出 **2 段**，第二段 `is_seg2 = True` |
| 3 | 组合帧分两批喂入（前 100 字节 / 其余） | 第一批 0 段，第二批 2 段 |
| 4 | 短帧（`51 07`） | 1 段，`data` 为空 |
| 5 | 前置噪声 `00 FF 12` + 短帧 + 组合帧 + 截断的帧 | 解析出 3 段，缓冲区剩 50 字节（截断部分保留待续） |
| 6 | 组合帧**逐字节**喂入 | 累计解析出 2 段，缓冲区清空 |
| 7 | 两帧连发逐字节喂入 | 累计 2 段 |
| 8 | 纯垃圾数据（300 个 `0x7F`） | 0 段，不死循环，缓冲区最终清空 |

> 场景 3、6、7 是重点 —— 它们验证「数据不足时必须等待而不是丢弃」。
> 这也是最容易写错的地方（见下面的实现提醒）。

### 实现提醒：两种帧的「未收全」处理

```
数据不足 → break（保留缓冲区，等下次通知追加）
CRC 失败 / 结构非法 → 丢掉 1 个字节后重找帧头
```

搞反会导致两种典型故障：

| 错误写法 | 后果 |
|---|---|
| 数据不足时滑动丢弃 | 跨通知的长帧永远解析不出来 |
| CRC 失败时不滑动 | 一旦错位就永久卡死，后面所有报文都收不到 |

### 实时数据解码

用厂商测试向量（186 字节数据区，见 [第 5.8 节](05-实时数据.md#58-完整解码示例)）验证：

| 字段 | 期望值 |
|---|---|
| 权限 | 5 |
| 电池状态 | 1（静止） |
| 单体数 N / 温度数 M | 24 / 4 |
| 第 1 串电压 | 3.877 V |
| 温度 1~4 | -40 ℃ |
| 总电压 | 92.3 V |
| 电流 | -0.1 A |
| SOC / SOH | 73 / 100 |
| 最高单体 | 3.909 V @ 第 16 串 |
| 最低单体 | 3.777 V @ 第 8 串 |
| 压差 | 0.132 V |
| 平均单体电压 | 3.845 V |
| 电池类型 | 64241（三元锂） |
| 告警位 | 充电 MOS 开、放电 MOS 开 |

**一致性自检**：`平均电压 × 串数 ≈ 总电压`（3.845 × 24 = 92.28 ≈ 92.3）；
`最高 − 最低 = 压差`（3.909 − 3.777 = 0.132）。
把这两条做成单元测试断言，能有效防止偏移算错。
