## 6.1 参数区模型

参数区是一个**以字节为单位寻址的 u16 数组**：

```
地址:  0     2     4     6     8     ...   152   154  ...
      ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐
      │参数0│参数1│参数2│参数3│参数4│ ... │类型 │串数 │ ...
      └─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘
      每个参数固定 2 字节（u16 小端）
```

规则：

- **地址 = 字节偏移**，而不是「第几个寄存器」。
  所以「第 k 个参数」的地址是 `2k`。
- 每个参数固定 2 字节，**没有 1 字节或 4 字节的参数**。
  需要 32 位量（如容量）时，用连续两个地址表示，或整体按 u32 读。
- 全表地址 0 ~ 786，完整清单见 [附录 A](附录A-参数寄存器表.md)。

工程量换算：

```
工程量 = 原始整数值 ÷ 倍率
```

| 参数类型 | 倍率 | 例子 |
|---|---|---|
| 单体电压类阈值 | 1000 | 地址 0 = 3650 → 3.650 V |
| 总压类阈值 | 10 | 地址 8 = 584 → 58.4 V |
| 电流类阈值 | 10 | 地址 104 = 1000 → 100.0 A |
| 温度类阈值 | 1 | 地址 56 = 55 → 55 ℃ |
| 容量 | 1e6 | 地址 162 → Ah |
| SOC / 串数 / 开关 | 1 | 直接使用 |

## 6.2 读参数（0x02 → 0x12）

> ✅ **实测已验证**（2026-09-29 · 真板 `ANT@BLE24CBUB-3547`，固件 `24CBUB02-240623C`）：实测分块读全部成功，应答长度与请求字节数一致。

### 请求（短帧）

```
7E A1 02 <地址2B 小端> <字节数> CRC AA 55
```

- 寄存器 = **起始地址**（字节偏移，小端）
- 长度 = **要读取的字节数**（必须是偶数，因为参数都是 2 字节）

示例：读位置 104 开始的 32 字节（即地址 104 ~ 135，共 16 个参数）

```
7E A1 02 68 00 20 18 65 AA 55
         └─┬─┘ └┬┘
   寄存器 = 0x0068 = 104
               长度 = 0x20 = 32
```

### 应答（长帧）

```
7E A1 12 <地址2B> <长度> <数据> CRC AA 55
```

数据区就是**原始 u16 小端序列**，按顺序对应地址：

```
数据[0..1] → 地址 0
数据[2..3] → 地址 2
数据[4..5] → 地址 4
...
数据[2k..2k+1] → 地址 起始地址 + 2k
```

参考实现：

```python
def parse_params(data: bytes, start_addr: int, ratios: dict) -> dict:
    out = {}
    for k in range(0, len(data) - 1, 2):
        addr = start_addr + k
        raw = data[k] | (data[k+1] << 8)
        ratio = ratios.get(addr, 1)
        out[addr] = raw / ratio
    return out
```

以下分块方式来自旧版 App 各参数页面的实际读取请求，可直接照用：

| 起始地址 | 字节数 | 内容 | 页面 |

| 56 | 44 | 温度保护与告警阈值（56 ~ 98） | 温度参数页 |
| 104 | 32 | 电流保护/告警、SOC 告警（104 ~ 135） | 电流参数页 |

| 152 | 142 | 电池类型、串数、容量、SOC 电压表、内阻、电池 ID（152 ~ 293） | 电池组参数页 |
| 298 | 34 | 传感器量程、待机时间、蓝牙编码、基准电压（298 ~ 331） | 系统参数页 |
| 378 | 18 | 其他参数（378 ~ 394） | 其他参数页 |

> 但注意长度上限 192 字节。

## 6.4 写参数（0x22 → 0x42）

> ✅ **实测已验证**（2026-09-29 · 真板 `ANT@BLE24CBUB-3547`，固件 `24CBUB02-240623C`）：实测 `0x42` 数据区确为参数块回显（写被拒时同样回显）；结果码在同帧追加的 `0xFF` 段。

### 请求（长帧）

```
7E A1 22 <地址2B> 02 <值2B 小端> CRC AA 55
```

- 寄存器 = **参数地址**（字节偏移）
- 长度恒为 `02`（单参数写只写 2 字节）
- 数据 = 值的小端表示

### 值编码流程

```
工程量 → ×倍率 → 向下取整 → 十六进制（定长 4 位） → 字节倒序 → 写入数据区
```

示例：把单体过压保护（地址 4，倍率 1000）写为 3.650 V

```
3.650 × 1000 = 3650 = 0x0E42
字节倒序 → 42 0E
帧：7E A1 22 04 00 02 42 0E 4C 2C AA 55
        └─┬─┘ └─┬─┘ └┬┘ └─┬─┘
    功能码22 地址4  长度2 数据
```

参考实现：

```python
def encode_value(value: float, ratio: int) -> bytes:
    raw = int(value * ratio)          # 向下取整
    raw = max(0, min(raw, 0xFFFF))    # 夹到 u16 范围
    return bytes([raw & 0xFF, raw >> 8])

def build_write(addr: int, value: float, ratio: int, dev=0xA1) -> bytes:
    data = encode_value(value, ratio)
    body = bytes([dev, 0x22, addr & 0xFF, addr >> 8, 2]) + data
    crc = crc16_modbus(body)
    return b'\x7E' + body + bytes([crc & 0xFF, crc >> 8]) + b'\xAA\x55'
```

### 应答（长帧）

```
7E A1 42 <地址2B> <长度> <数据区 = 参数块（u16 小端数组）> CRC AA 55
```

**关键点：`0x42` 的数据区不是「1 字节结果码 + 数据」，而是参数数据块本身**，
布局与 `0x12` 完全一致。旧版 App 的解析器里明确写着：

```javascript
if (18 == e[2] || 66 == e[2]) {      // 0x12 与 0x42 走同一个解析函数
    // 按 u16 小端数组写入本地参数缓存 BatteryParams
}
```

也就是说：写成功后，设备会回传**从该地址开始的参数块**（具体回传多少字节由设备决定），
客户端按起始地址 + 长度存进本地缓存，不需要额外再读一次。

> 这也解释了为什么"写参数后读不到结果码"——**结果码不在这里**。

### 写失败时的提示从哪来

写失败（超限、越界、权限不足）时，设备会在**同一帧里追加一段功能码 `0xFF` 的第二段**
（组合帧，见 [第 3.3 节](03-帧格式与校验.md#33-组合帧)），旧版 App 用 `A()` 函数解析：

```
7E A1 42 ... CRC1 | FF <结果码1B> <未明1B> <长度> <参数地址 u16> <限值 u16> CRC2 AA 55
                    └──┬───┘
            结果码位于寄存器低字节
```

> 上述字段位置由旧版解析器 `A()` 的取址反推：结果码取第 3 字节、
> 长度取第 5 字节、参数地址与限值取第 6~9 字节（均为小端 u16）。
> 第 4 字节的角色在源码中未出现，推测是寄存器高字节（未使用）。

| 结果码 | 含义 | 附带数据 |
|---|---|---|
| 0 | 正常 | — |
| 1 | 权限不够（提示去校验权限） | — |
| 2 | **数据小于最小值** | 参数地址 + 允许的最小值 |
| 3 | **数据大于最大值** | 参数地址 + 允许的最大值 |
| 4 | 地址超范围 | — |
| 5 | 电池类型错误 / 密码不正确 | — |
| 10 | 设置成功（需保存后生效） | — |
| 11 | 读取成功 | — |
| 17 | 固件不匹配 | — |

> 客户端把「限值」除以该参数的倍率后展示，例如「当前允许最小值为 2.500」。
> 这套结果码与 `0x63`（DTU 命令应答）共用同一码表，详见 [附录 B.6](附录B-命令码表.md#b6-dtu-结果码0x63-应答)。

### 新版如何处理

新版不硬编码这套结果码，而是**按服务端下发的协议模板解析**：
模板把响应字段命名为 `xxx_success` / `xxx_error_min` / `xxx_error_max`，
App 见到 `_success` 字段为真即判成功；见到 `_error_min` / `_error_max`
就用模板里的 `range` 把值换算成工程量后提示用户。

## 6.5 结果码与失败提示

> ✅ **实测已验证**（2026-09-29 · 真板 `ANT@BLE24CBUB-3547`，固件 `24CBUB02-240623C`）：实测 `0xFF` 段：码 1 = 权限不够（附参数地址）、码 11 = 读取成功（每次读应答都跟一条）。

参数写入的结果**不在 `0x42` 的数据区里**（见 [6.4 节](#64-写参数0x22--0x42)），
而是由追加的 `0xFF` 段（失败时）或后续 `0x61` 应答（保存时）携带。
涉及的码表有两套，别混用：

| 码表 | 出现位置 | 取值 |
|---|---|---|
| **写参数结果码** | `0xFF` 附加段 | 0 正常 / 1 权限不够 / 2 小于最小值 / 3 大于最大值 / 4 地址超范围 / 5 电池类型错误 / 10 设置成功 / 11 读取成功 / 17 固件不匹配 |
| **控制结果码** | `0x61` 应答 | 1 成功 / 2 失败 / 3 权限不足 / 4 地址超范围 / 5 电池类型错误 / 6 电流(电池)信息错误 / 7 固件不匹配 |

完整的取值表见 [附录 B.2](附录B-命令码表.md#b2-控制结果码0x61-应答) 与 [附录 B.3](附录B-命令码表.md#b3-写参数结果码0xff-附加段)。

失败时设备会带上「出错的参数地址」与「允许的限值」，
客户端把限值除以该参数的倍率后提示用户，例如「当前允许最小值为 2.500」。

## 6.6 保存与生效

> 🟠 **实测部分验证**（2026-09-29 同上）：实测 `51/07` 帧发出并收到 `0x61` 应答（该机权限不足返回码 3）；**保存成功后的掉电持久化未验证**（需 ≥3 级权限）。

**写参数不会立即生效**，也不会自动写入 flash。标准流程：

```
① 校验权限（若权限 < 3）
     7E A1 23 4A 01 08 <8字节密码> CRC AA 55

② 逐个写入要改的参数
     7E A1 22 <地址> 02 <值> CRC AA 55
     （每个都返回结果码 1 = 成功）

③ 发送"保存应用参数"
     7E A1 51 07 00 00 38 E4 AA 55

④ 等待 0x61 应答，结果码 1 = 保存成功（码表见 [第 7.3 节](07-控制命令.md#73-应答与结果码)）
```

为什么必须第 ③ 步：BMS 内部把参数分「临时区」和「存储区」，
`0x22` 只写临时区（掉电丢失），`51/07` 才把临时区固化到 flash。

参数页面的保存按钮在 App 里对应的就是这几步；用户改完不点保存，重启后会恢复原值。

### 写入结果的两条来路（容易搞混）

```
                                        ┌─ 成功 → 0x42 回显参数块（客户端刷新缓存）
发 0x22 写参数 ─────────────────────────┤
                                        └─ 失败 → 同一帧追加 0xFF 段（携带结果码 + 地址 + 限值）
发 0x51 07 保存 ───────────────────────→ 0x61 应答（结果码 1=成功，其余见 0x61 码表）
```

两条来路的**码表不同**：`0xFF` 段用「写参数码表」（0 正常 / 2 小于最小值 / 3 大于最大值…），
`0x61` 用「控制码表」（1 成功 / 2 失败 / 3 权限不足…）。解析时按功能码选表。

## 6.7 读取特殊区块（版本 / ID / Code Key）

> ✅ **实测已验证**（2026-09-29 · 真板 `ANT@BLE24CBUB-3547`，固件 `24CBUB02-240623C`）：实测读回：Boot `BT24CBUB-240616A`、硬件 `24ZHE6TB130A`、软件 `24CBUB02-240623C`、电池组 ID 32 字节；Code Key 该机未编程（全 `FF`）。

这些区块虽然也在参数区地址空间里，但内容是**字符串**，解码方式不同于普通 u16：

| 地址 | 长度 | 内容 | 解码 |
|---|---|---|---|
| 262 | 32 | 电池组 ID（pack_id） | 每 2 字节取低字节拼成 ASCII，去尾部 `0x00` |
| 528 | 16 | Boot 版本号 | 同上 |
| 576 | 16 | 系统 Code Key | 每个 u16 的低字节、高字节依次转**十进制**并用 `.` 连接 |
| 620 | 16 | 硬件版本 | 每 2 字节取低字节拼 ASCII |
| 636 | 16 | 软件版本 | 同上 |

示例：读版本（地址 620，32 字节）

```
请求：7E A1 02 6C 02 20 58 C4 AA 55
应答数据区前 16 字节 → 硬件版本 ASCII（如 "V1.2.3"）
```

Code Key 的解码比较特殊（旧版实现）：

```javascript
for (i = 0; i < 8; i++) {
    lo = params[288 + i] & 0xFF;          // 低字节
    hi = (params[288 + i] >> 8) & 0xFF;   // 高字节
    str += "." + lo + "." + hi;
}
```

即把两个 u16 的 4 个字节都转成十进制字符串再用 `.` 连接（去掉开头的点）。
这类字段主要用于设备授权/加密校验，普通应用读到即可，不必还原语义。

## 6.8 新版批量读写

新版把参数定义放在了**服务端下发的协议模板**里，App 只做「命令名 → 命令码」的映射：

| 概念 | 说明 |
|---|---|
| `dataPos` | 参数地址（与本表一致） |
| `readCode` | 读取功能码（通常是 `02`） |
| `writeCode` | 写入功能码（通常是 `22`） |
| `dataType` / `range` | 决定值的编码方式与倍率 |
| `define` | 参数的中文名（国际化 key） |

批量写入由 `sdk/api/common/utils/bleBatchCommandExec.js` 驱动，语义是**逐条发送、逐条校验**：

```
对每个待写参数（按顺序）：
  ① buildCommand("22", 参数名, 值)          → 组出该条的十六进制帧
  ② publishMessageWait(帧, 期望应答, 超时)    → 发送并等待应答
  ③ ackCheck(应答, 期望功能码, 期望寄存器)     → 校验「功能码 + 寄存器」是否匹配
  ④ 通过则进入下一条；失败则中止并回调 onError
全部通过后：
  ⑤ buildCommand("51","saveAppParamters") → 发 51/07 保存
```

它提供四个回调用于界面反馈：`onProgress`（第几步）、`onStepSuccess`（单条成功）、
`onError`、`onComplete`。

> **关键点：不是「盲发一批」**。每一条都要等应答并用 `ackCheck` 校验功能码与寄存器
> （与 [第 12.3 节](12-固件升级.md) 里升级应答的校验机制是同一个）。
> 自研实现时若连续盲发多条写命令，很容易因 BMS 处理不过来而丢包或错位。

批量读取则用「读命令组」概念（`bulkReadCommands`），
一次请求读回一整块参数（本质上与 [6.3 节](#63-常用读取块) 的分块读取相同，
只是长度由模板给定）。

> **自研实现的建议**：不需要复刻模板机制。
> 直接按 [6.3 节](#63-常用读取块) 的分块读 + [6.4 节](#64-写参数0x22--0x42) 的单点写，
> 再配合 `51/07` 保存即可，行为与官方 App 等价。

## 6.9 真机实测补充（2026-09-29，ANT@BLE24CBUB-3547 / 固件 24CBUB02-240623C）

以下都是这条真板上抓到并逐帧核对过的，用于给实现定边界（协议细节与前面各节一致，这里补的是**操作层面**的实测边界）。

### 读参数

- 分块读 [6.3 节](#63-常用读取块) 的 6 个块 + 身份区 5 块，**一轮可稳定读回 157 项**（0x12 应答长度与请求字节数一致）。
- 每条 `0x12` 应答后都紧跟一段 **`0xFF` 段，码位 11 = 读取成功**：
  `func=FF reg=11 len=0`。它是每帧的读状态回执，**不要**把它当写参数结果（见 6.5 节的码表分工）。
- ⚠ **实测权限门槛**：**一级权限下保护参数区整块返回 `0xFFFF`**（身份区 528/620/636 仍正常）。
  升到二级后同一块立刻拿到真值。实现建议：
  读到 `0xFFFF` 视为「未获授权」→ 界面显示 `--`，并提示需要 ≥2 级；不要把 65535 当数值渲染。
- 系统参数块读到 **328 为止即可**，330 起是密码区，没必要把密码字节读进内存。

### 写参数

- `0x42` 的数据区确实是**参数块回显**（与 `0x12` 同布局）——实测**写被拒时也照样回显**，
  所以「收到 0x42」≠「写成功」，必须看同一帧追加的 `0xFF` 段。
- 实测一条被拒的完整交互（二级权限写单体过压保护）：

```
TX 7E A1 22 00 00 02 CC 10 58 44 AA 55      ← 写地址 0 = 0x10CC (4300 = 4.300 V)
RX 7E A1 42 00 00 02 CC 10 … AA 55          ← 0x42 回显参数块
RX func=FF reg=1 len=4 00 00 03 00          ← 0xFF 段：码 1 = 权限不够（附地址 0）
```

- **写参数与控制命令需要 ≥3 级权限**（该机二级下写参数/控制均被拒：`0xFF` 码 1、`0x61` 码 3）。
- 容量类是 u32 跨两格（见 [附录 A](附录A-参数寄存器表.md) 表头）：`0x22` 一次只写 2 字节，
  改容量必须**连写两帧**（低字 @162、高字 @164），否则 113.0 Ah 会被截断成低 16 位。
- 弱信号下 `0x42` 与 `0xFF` 段到达可能相差数百毫秒；判定结果前给 ~200 ms 收尾时间更稳。
- 请求与应答要**同时比对功能码和寄存器**：只比功能码会把上一条超时命令的迟到应答收下
  （实测踩过：三级密码校验收下了二级的应答，日志显示「用 3 级密码，设备当前权限 2 级」）。
