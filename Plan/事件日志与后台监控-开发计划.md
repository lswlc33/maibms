## 1. ① 事件日志与保护计数

### 1.1 协议（双源对照后的定论）

**请求**（短帧，与官方 `ReadData` 逐字节一致）：

| 操作 | 帧 | 说明 |
|---|---|---|
| 读第 N 条日志 | `7E A1 03 <N 小端2B> 00 CRC AA 55` | 长度字段 = `00`；官方与文档一致 |
| 读 20 个计数器 | `7E A1 05 00 00 28 CRC AA 55` | **长度字段 = `0x28`(40)**，不是文档写的 `00`——官方 `helper.js ReadData(0,40,5)` 实测字节如此 |

读日志的 N 从 0 起算，**每读一条 N+1**（官方 `bmsLog.js`：请求序号 = `logList.length`）。

**应答**（长帧 `0x13`）数据区：

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 2 | 日志序号回显（**官方两个 BLE 解析器都不读它**，序号取帧头 reg） |
| 2 | 1 | 数据项条数 K |
| 3 | 1 | 事件类别码（1 基，1~133） |
| 4 | 4 | 时间戳 u32 小端 |
| 8 | 4×K | 数据项：`[项号1B][符号标志1B][值u16小端2B]`，符号标志 `0x80` = 按 s16 解读 |

**应答**（`0x15`）数据区：20 个 u16 小端连续排列（顺序见文档 C.3）。

### 1.2 三处与文档不一致，按反编译源码为准

1. **时间戳不是 Unix 秒，官方当「时长」显示**。旧版 `SecondToHour`、新版 BLE `SecondToHour`、
   新版 SDK `bms_common.formatDateTime` 三个实现全部格式化成「X天X时X分X秒」，
   没有任何一处转成日历日期（新版还把该字符串当 `eventSystemTime` 上传）。
   文档 §8.2/§8.7 的「Unix 时间戳」结论与实现对不上。
   **本项目做法：按取值自动判别**——`≥ 1.6e9`（2020-09 之后的 Unix 秒）按本地时间显示，
   否则按运行时长显示。两种固件行为都能正确呈现，且不需要真机就能自证（单测覆盖两侧）。
2. **「读到返回条数为 0 即停止」不存在**。官方判据是**帧长度字段**（`e[5]`/`l[5]` 为 0），
   新版更是取不到也继续补 `--` 占位、直到凑满一页 10 条。
   **本项目做法：长度字段为 0 或 K 为 0 或连续超时 → 判定到底**，比官方更严谨。
3. **数据项表不止 32 项**。新版 `dict.js` 给 33~37 号也定了名
   （未跳线前均衡串数 / 跳线后均衡串数 / 均衡故障码 / 加热mos状态 / HDSV），
   文档说 33~64 全是占位。**本项目做法：采用新表 1~37，38+ 按未知项处理**。

### 1.3 对文档「未知数据项」处理的修正

文档 §8.2 说未知项「把数据项号本身作为值显示」。核实后：**只有两个 BLE 解析器这么干，
而且是个 bug**——它们遇到未知项只吞掉 1 字节项号，符号标志与 2 字节值没读，
**导致同一条记录后续所有数据项全部错位**。新版 SDK 的 `bms_0x13` 则正常吞满 4 字节。
**本项目做法：未知项也吞满 4 字节**（不产生错位），显示为「未知数据项 N」。

### 1.4 实施

| 层 | 改动 |
|---|---|

## 2. ② 后台策略与告警通知

### 2.1 现状（问题）

`MaibmsApp` / `MainActivity` 无任何生命周期处理，轮询循环只要连着就一直跑：
**退到后台仍在按 600ms 轮询、占着 BLE 连接，却没有任何展示或通知**（全仓库零通知代码）。
电耗换不回任何东西，且系统随时会杀进程。

### 2.2 定案：一个开关决定两种行为

设置页新增「后台监控」（默认**关**）：

| 开关 | 退到后台的行为 | 通知 |
|---|---|---|
| 关（默认） | **暂停轮询**（保留连接，回前台立即恢复；连接被系统回收则走既有自动重连） | 无 |
| 开 | 前台服务保活 + 持续轮询 | 常驻「监控中」通知（含 SOC/电压摘要）+ **保护/告警首次触发**通知 + 失联通知 |

这样默认档比现状更省电，开启档才付出后台电耗，且电耗是可见的（常驻通知）。

### 2.3 实现要点

- **前台/后台信号**：`data/AppForeground.kt`（commonMain）一个 `MutableStateFlow<Boolean>`，
  默认 `true`；Android 侧在 `MaibmsApp.onCreate` 注册 `ActivityLifecycleCallbacks` 写入。
  **不新增 expect/actual**——桌面/iOS 保持 `true`，零改动零风险。
- **通知出口**：`ui/Notifications.kt`（commonMain）一个可注入接口，
  Android 侧按既有惯例注入实现（同 `AppStore.store` / `LogFileStore.setDir` 的写法）；
  未注入 = 空实现。**不写任何 iOS 代码**（Windows 上编不了 Apple 目标，
  写了无法验证，宁可留空并在此记录）。
- **常驻监控**：`androidMain/monitor/BmsMonitorService.kt`（`foregroundServiceType="connectedDevice"`）
  + 两个通知渠道（监控=低优先级常驻、告警=默认优先级）。清单补
  `POST_NOTIFICATIONS` / `FOREGROUND_SERVICE` / `FOREGROUND_SERVICE_CONNECTED_DEVICE`。
  服务只做「保活 + 通知」，BLE 与轮询仍归 Application 作用域的仓库，**不搬动既有架构**。
- **告警触发**：`data/AlarmNotifier.kt`——纯函数 `newlySet(prev, now)` 求**上升沿**（可单测），
  只报保护位全体 + 告警位 0~16（`BitDict.stateBits` 里的运行状态位不算告警，
  与卡片/详情弹窗共用同一过滤规则）。**仅在前台不可见时发**（前台时界面已有横幅，避免双提醒）。
- **节流**：同一位每次会话只报一次；整条通知合并（一帧多个位合并成一条，最多列 3 项 + 「等 N 项」）。
- **失联通知**：后台监控开启且退到后台时，`stalled`/链路断开各报一次。
- 点击通知 → 打开 `MainActivity`。

**实施中的若干取舍**（与初版计划的差异）：

- **进页只在"没数据"时自动读**：已有记录就不重读，避免每次切回这一页都读一遍设备；要最新的点「刷新」。
- **刷新失败不清空已显示的记录**：只挂横幅说明"读取中断"，已读到的仍然有效。
- **告警冷却取 5 分钟**（原计划 10 分钟）：保护在阈值附近来回抖动是同一个事故，一次提醒够；
  但真正隔了几分钟的第二次触发不该被"同类合并"吃掉。
- **日志页用 LazyColumn 自建布局**（不用 `ScreenScaffold` 的滚动 Column）：设备日志可翻到上百条，
  一次性布局几百行会明显卡（与开发者页日志列表同类的坑）。
- **公共代码不用 `expect/actual` 接平台通知**：改为"平台注入实现、未注入即空实现"（同
  `AppStore.store` 的做法），iOS/桌面零改动——Windows 上编不了 Apple 目标，写了也无法验证。
- 顺带修掉两处**与本轮相关**的旧问题：`SRow` 改等分双权重（长读数不再把标签挤没，
  大字号档下也不会）；详情弹窗限高可滚动（加了"运行状态"段后内容变长），
  且未收到过数据时不再合成"充电MOS关/放电MOS关"（位域全 0 ≠ MOS 确实是关的）。

**回归**：`desktopTest` 189 例全绿（本轮 +37）、`compileDebugKotlinAndroid`、
`compileCommonMainKotlinMetadata`（平台中立性——这一步抓到 `@Volatile` 在 commonMain 不可用，
不改会直接挂 iOS 编译）、`assembleDebug`、`:composeApp:shot` 全部通过。

## 6. 已知不确定（待真机）

1. 事件日志时间戳究竟是 Unix 秒还是设备运行时长——本轮按取值自动判别，两种都能正确显示；
   真机读一条日志即可确认（取到的值与设备当前运行时间对比）。
2. `0x15` 应答是否真为 40 字节数据区（20 项）——按官方请求长度 40 与文档 20 项表实现，
   真机确认项数与顺序。
3. 保护计数的清零命令（51/37）是否连带清日志（51/15）——两者独立，真机各点一次确认。
4. 后台常驻监控的实际存活时长与厂商 ROM 保活情况（需真机 + 特定 ROM）。
5. 主动均衡机型下 `T0+36` 应解读为结构体而非均衡位图（本轮**不做** 0xFE 机型识别，
   该隐患仍存在，见上一轮评估的板块③）。
